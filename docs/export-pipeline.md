## 一、入口与产物形态

| 场景 | 操作 | 结果 |
| --- | --- | --- |
| 单篇 | 笔记列表右键 / 阅读界面右键 → “导出为 Markdown” | 没有要落盘的图片 / 附件时给 `.md`（或 `.html`）；勾了下载、且有东西要落盘时给 `.zip`（内含 `images/`、`attachments/`） |
| 多篇 | 列表里多选后右键 → “导出为 Markdown（N 篇）” | 一个 zip，每篇一个与标题同名的文件夹；同标题加 ` (2)` 后缀区分（见 §1.4） |

打包规则有个刻意的设计：**只要产物里还有要落盘的本地资源（图片或附件）、且用户勾选了下载，就一定打包成 zip**，哪怕一个都没下下来。因为退化成裸 `.md` 会让它的 `images/xxx.png`（或 `attachments/xxx.pdf`）引用全部悬空 —— 表面成功、实际丢图。这种情况下 zip 里只有 md，但结果区会明确写出“图片 0/3 张”“附件 0/1 个”以及“《标题》有 3 张图片没取到”。

导出 HTML 的那几类笔记同理（见 §4.6）：附件同样要落盘、页面里那个附件链接也会被改成相对路径，所以有附件就照样打包，zip 里 `attachments/` 与 `.html` 并列。

**正文为空的笔记照常导出**，不跳过、也不算问题：空笔记同样是正常笔记，标题 / 创建时间 / 分类 / 标签都是信息，产物就是 front matter（有评论或附件时再拼上相应章节；勾了元数据就有内容，没勾元数据时是一个 0 字节的 `.md`，文件名仍然是标题）。早先这里会 `return { ok: false, detail: '笔记内容为空，已跳过' }`，会让用户以为丢了一篇。同理，正文为空也**不能**丢掉评论章节 / 附件章节（否则结果区报“评论 3 条”，产物里却一句话都没有）。

### 1.1 文件留在浏览器手里，可以重复下载

导出结束后产出的 `Blob`（形态与内存口径见 §1.9）不会立刻丢掉，对话框会在底部给出一个下载按钮：

| 时机 | 按钮 | 说明 |
| --- | --- | --- |
| 正常完成 | “重新下载”（主） | 同时已自动下载过一次；浏览器把自动下载拦掉、或被用户关掉下载弹窗时，点它再下 |
| 被中止 | “下载已完成部分”（主） | **不自动下载**（用户刚喊停，再弹文件很怪），只把已打好的部分 zip 留着由用户决定（中止后还要打完包，见 §1.8） |
| 没有产出 | 隐藏 | 例如所有笔记都被跳过 |
| **选项被改过** | 隐藏，只剩“再次导出” | 手上这份文件已经和界面上的选项对不上，不能让它冒充新选项的结果 |

最后一条靠**选项指纹**实现：导出开始时把当时的选项压成一个字符串（`currentOptionsKey()`），结果出来后每次渲染都比一次，不一致就收起下载按钮；改回去又会重新出现。所以用户在结果页上可以直接试验“换一组选项会怎样”，而不会误把旧文件当成新结果下载走。

之所以要单独一个按钮，而不是让用户点“再次导出”：

- **“再次导出”代价完全不同** —— 会重新拉图、重新同步协作笔记，耗时且结果可能变（笔记被改过、某张图这次没取到）。
- **选保存位置只能在用户手势里做** —— 浏览器只允许在有用户手势时打开保存对话框，而导出完成是异步回调，那里没有手势。想让用户自己选目录，就必须有一个可点的按钮。

Blob 挂在**任务**上（`ExportTask.file`），保留到任务被关掉为止（关闭即释放），再次导出会覆盖上一份。任务收进悬浮条之后文件照样留着，随时能从悬浮条上下载。实现见 `src/export/session.ts` 与 `src/ui/export-tasks.ts`。

### 1.2 关闭弹窗的几种手势

规则容易在重构时被顺手改掉，显式记在这里：

| 手势 | 草稿（检查中 / 待导出） | 排队中 / 导出中 | 已结束 |
| --- | --- | --- | --- |
| 右上角按钮 | 关闭（丢弃这个草稿） | **最小化**（按钮变成 `−`，不中止任何东西） | **最小化**（按钮同样是 `−`，结果与文件都留着） |
| 按 Esc | 同上 | 同上 | 同上；**确认行亮着时只收确认行**（停在对话框里） |
| 底部按钮 | 取消（丢弃草稿） | **中止 / 取消排队** —— 中止**要二次确认**，取消排队不必 | 关闭（**要二次确认**：会清掉这批记录与产出的文件） |
| 点模态框外部空白 | **不关闭** | 不关闭 | 不关闭 |

点空白是最容易误触的手势（中途一慌就乱点），干脆不作为“收起弹窗”的入口，遮罩只负责挡住下层页面。

**为什么右上角一直不用二次确认**：它对**已开始的任务**（排队 / 导出中 / 已结束）一律是“最小化”——**无副作用**的动作，随手点错也没有代价（任务还在，悬浮条上点得回来，产出的文件也还在），因此不需要拦一道。

**底部按钮什么时候要二次确认**：只看这一刻它会不会丢掉**已经产生的东西** —— 于是四个文案各自有了归宿：

| 按钮（阶段） | 丢掉什么 | 确认？ |
| --- | --- | --- |
| 中止（跑着） | 停在当前这一篇（它整个作废，§1.7）+ 剩下还没处理的那些篇 | **要**。后果里点名“还有 N 篇不会再处理”，并留“继续导出”的退路 |
| 关闭（已结束） | 这批导出记录 + 那份 Blob（§1.1；自动下载被浏览器拦掉时它就是唯一的文件） | **要**。同样先亮确认行，说白“会掉什么”，留“继续查看” |
| 取消排队（排队中） | 只丢这次的选择（还没开始导、什么都没产出） | 不要 —— 拦一道只会让人多点一下 |
| 取消（草稿） | 草稿本身；与右上角 × / Esc 同一语义（即点即弃） | 不要 |

确认行亮起来之后，**触发按钮自己变成不可用**（`aria-disabled` + 交还 hover 底色，见 §1.6），直到在那条行里选一个 —— 屏幕上“这一下会不会真的执行”永远只有一个答案。

> 中止的确认是**后加的**：原先的理由是“它的文案已经写明了后果”，所以放过了它。改主意的原因是那一步丢掉的不是一条记录，而是**几十篇还没处理的活**，且没有回退 —— 想接着导只能重新发起一次，那会把已经导过的部分再走一遍（§1.1：重新拉图、重新同步协作笔记）。

任务一进队列（以及跑完之后）头部下方的**横幅**会提示“可以点右上角的 − 收起来”，否则没人会想到那个 × 已经换了含义。两处**不再互斥**：横幅是通知、确认行是决策（见 §1.6），可以同时挂着。

这套规则由 `src/ui/kit/modal.ts` 的**模态壳**实现：× 与 Esc 都交给调用方的 `onDismiss(source)`，壳自己从不擅自关闭；按钮的文案与 aria-label 由调用方按任务状态改写（`ModalHandle.closeButton`）；“点空白不关闭”也是壳的一部分。设置对话框用的是同一个壳，但它没有“跑着的任务”这回事，× 恒为关闭 —— 要改这些规则前先想清楚是不是两个对话框都该跟着改。

**焦点也归这个壳管**（两个对话框共用同一套，改之前同样要两边一起想）：

| 时机 | 行为 |
| --- | --- |
| 打开 | 焦点落到 `dialog` 容器**自己**（`tabindex="-1"` + `aria-labelledby` 指向标题）—— 读屏因此先念“这是个对话框、叫什么名字”，而不是直接念第一个按钮。接焦点在入场那一帧（内容已由调用方填好） |
| `Tab` / `Shift+Tab` | 在对话框内**环绕**（`trapTab()`）。遮罩底下就是宿主页面的一整屏界面，不拦的话焦点会走进用户看不见的那一层 —— 而 `aria-modal="true"` 已经向辅助技术承诺了“外面不可达” |
| 焦点跑到外面时按 `Tab` | 也管：点过遮罩空白就会这样，那一下先把焦点收进第一项（`Shift+Tab` 收进最后一项），而不是放任它从页面某处继续往下走 |
| 点遮罩空白 | 仍然**不关闭**（见上表），同时用 `mousedown` 的 `preventDefault()` 把焦点留在原处 —— 点在一个不可聚焦的元素上，浏览器会把焦点丢回 `body` |
| 关闭 | 焦点还给**打开它的那个元素**（`createModal()` 进来时记下的）。时机是遮罩摘掉之后**再等一帧**：最小化那条路径要等调用方的 `setExportDialogOpen(false)` 摘掉“悬浮条藏起来”的 class，而 `visibility: hidden` 的元素**收不到焦点**（§1.5 那条接力的顺序也是同一个道理）。元素可能已经不在了（右键菜单项点完即拆），还不了就什么都不做，不去抢页面别处的焦点 |

> 页面那一层**没有**做 `inert`：那要动宿主文档 `body` 的子节点（宿主是 React 应用，随时可能重建），收益与“万一没摘干净，整页都点不动了”的风险不匹配。键盘那条路已经由焦点环绕堵住，辅助技术那边由 `aria-modal` 负责 —— 要补 `inert` 的话，先把这两处的不对称想清楚。

“焦点还给打开它的那个元素”有一类**壳办不到的**情况：那个元素被**拆掉重建**了 —— 悬浮条的任务行就是这样（任务一进对话框就不再算“收起来的”，整条悬浮条连同行一起被拆掉；收起之后重建的是新节点）。壳只按“原节点还在不在文档里”判断，这一种由那一侧接着还：`ui/export-tasks.ts` 在**拆行之前**记下焦点所在行的任务 id（`rememberRowFocus()`），等对话框收完的那次广播里，若焦点确实没处可去就把它放到**同一个任务**的新行上（`restoreRowFocus()`）。落点因此是“同一个东西”，只是换了个节点。

收起现在是**带动画**的（`close(to)` 给的落点，见上文“悬浮条与对话框之间的接力”）：遮罩与对话框两三百毫秒后才真的从 DOM 上摘掉，中途那层会被置成 `pointer-events: none`、也不再接 Esc。**手势的裁决一点都不受影响**，只是最后那一下“消失”不是瞬时的 —— 别把这段动画误当成新的状态。

> ⚠️ 靠 `hidden` 控制显隐的元素，作者样式里的 `display` 会盖掉 UA 的 `[hidden] { display: none }`（实测踩过：确认条写了 `display: flex`，于是 `el.hidden = true` 之后它照样占位）。所以 `panel.css` 顶部有一条 `[hidden] { display: none !important }` 兜底，别删。
>
> 需要靠 `hidden` 收起的节点因此都不能带作者 `display` —— 头部横幅与确认行都是**两层**：外层（`.wze-modal-banner` / `.wze-confirm`）只负责被补间的高度、不带任何作者 `display` 与 padding，内层（`-inner`）才写 `display: flex` 与间距。悬浮任务条是靠 `visibility` 藏的（§1.5），不在此列。

**两个槽出现 / 收起都是补间**：头部横幅走 `modal.setBanner(show)`、底部确认行走 `ui/kit/confirm.ts`，两者都是 0 ↔ 自然高度的 `setRevealed()`。调用方（导出对话框每帧调一次、设置对话框想起来才调）**不用自己记状态**：`setBanner()` 在“状态没变”时什么都不做（另存一份“上次开着还是关着”迟早漏一处），收起动画跑着的那 160ms 里它也已经算收起了。

> 唯一的例外是**跟着对话框一起生出来的那条**：它和对话框的入场变形本来就是同一件事，再自己长一下只会多出一拍。判据在壳里 —— 入场补间（下一帧才跑）还没开始的这轮同步建 DOM 中调用的 `setBanner()` 直接落定；对话框已经落定之后再出现的（点“开始导出”后那条“可以点 − 收起来”、设置里那条“需要刷新”）才带补间。

阅读界面用编辑器自带的右键菜单（`LiveEditor` 的 `contextMenu` 实例），我们在里面追加一项；列表用应用自带的 MUI 菜单（`#context-menu-note-list`），同样追加一项。

### 1.3 注入的菜单项要和邻居完全对齐

应用菜单项的外观挂在 **`.MuiMenuItem-root` 这套 class 上，不是从容器继承的** —— 只挂 `menu-item` 的话，左边距会比邻居少 8px（实测应用项是 `margin: 0 8px; padding: 6px 16px; border-radius: 6px; font-size: 14px; line-height: 21px`，高度 33px；我们少的就是那个 margin）。

所以 `buildListItem()` 把**同一套 MUI 稳定类名**挂到注入的 `li` 上：

```
MuiButtonBase-root MuiListItem-root MuiMenuItem-root MuiMenuItem-gutters MuiListItem-gutters MuiListItem-button
```

让应用自己的规则来管（连 hover 底色、圆角、字体一起跟随，暗色模式也不用单独处理）。`style.css` 里对应的 `.wze-menu-item` 规则一律用 `:where()` 把特异性压到 **0**，只作兜底 —— 否则两套值会打架，谁赢取决于样式表注入顺序。

**位置**：应用自己那组项在一个内层 `MuiList` 里，我们把自己挂到**外层 `ul` 的末尾**，即整张菜单的最后一项。不要去改应用那个 React 管理的列表，免得它重建时把我们抹掉。

> 应用本身**已经有**“导出为Markdown”菜单项，但 Web 版把它藏起来了（条件里带 `window.wizApp.isElectron`），而且官方实现只覆盖协作笔记和 Lite Markdown 笔记两类、还依赖 Electron 的 `shell.showSaveDialog`。所以这里是重新实现的一套。

### 1.4 文件与目录名的合法化与唯一化

zip 里的每一个名字（文件夹、正文文件、`images/`、`attachments/`、批注图层、sidecar）都由 `src/export/naming.ts` 决定，**两道工序、顺序不能反**：

1. **对齐上游** —— `convertToValidFilename()` 复刻应用自己的函数，只把非法字符换成空格。刻意与上游一字不差，这样“我们和应用的命名差异”能一眼看出是**加固**而不是**另一个实现**；
2. **落盘加固** —— `portableName()` 在上游结果之上再修到跨文件系统安全。

加固的四类都是“不修就真会出问题”的（`npm run check:naming` 逐条钉住）：

| 项 | 为什么必须修 |
| --- | --- |
| 控制字符 | 粘贴来的标题里很常见（front matter 那边也在专门测）；文件名带 `\n` 会坑 shell 与解压器 |
| 尾部点号 / 空格 | Windows 会**静默去掉**，等于替我们改名 —— `报告.` 这个目录会被改成 `报告`，可能正好撞上另一篇《报告》 |
| Windows 保留名 | `CON` / `PRN` / `AUX` / `NUL` / `COM1-9` / `LPT1-9`（**带扩展名也算**，`con.txt` 同样被占用；上标 `COM¹` 从 Windows 11 起也算）。在这些名字上 Windows **根本创建不出文件** |
| 超长 | ext4 / APFS 的单个组件上限是 **255 字节**，中文一字 3 字节 → 约 85 个字就撞线；而附件名是**用户上传时自带的**，中文长标题的 PDF 很常见。截到 **200 字节**（`NAME_BUDGET_BYTES`）是给同一篇的派生名（`<标题>.md` / `.html` / `.meta.json`）和撞名后缀 ` (N)` 留余量 |

⚠️ **加固与截断会制造新的撞名**（两个长标题截断后可能一模一样），这类撞名已经被下面的分配器自动兜住 —— 两者是配套的，不需要额外逻辑。

然后是**唯一化**：

- 撞名时加后缀 ` (N)`，N 从 2 起，**原名里的字符一个都不改**（所以文件名仍能看出原始标题）；
- 文件插在**最后一个 `.` 之前**（`1.pdf` → `1 (2).pdf`），目录一律追加到末尾（`v1.0` → `v1.0 (2)`，不是 `v1 (2).0`）；
- 查重用的 key 做 **NFC 归一化 + 大小写折叠**，落盘用的仍是原名。

两个**作用域**复用同一个分配器，靠 `scope` 隔开；整条链路上只有 `naming.ts` 一处决定名字：

| 作用域 | 覆盖 | 相对谁唯一 |
| --- | --- | --- |
| archive 级（`task.ts`） | 文件夹名、正文文件名、根级 sidecar | 整个 zip |
| 每篇目录级（`ResourceNamer`） | `images/`、`attachments/`、批注图层 | 该篇笔记目录内（按子目录分开，`images/x.png` 与 `attachments/x.png` 不冲突） |

**为什么查重要折叠**：Windows（NTFS）与 macOS（APFS / HFS+）默认**大小写不敏感**，部分还做 Unicode 归一化。不折叠的话，两篇标题只差大小写的笔记在解压时会落到同一个文件、互相静默覆盖。代价是大小写敏感的 Linux 上会多出一些 ` (2)` —— 宁可多改名，不可静默覆盖。

**消歧只落在文件夹上，不改正文文件名**：多篇导出时每篇一个与标题同名的文件夹，同标题靠文件夹加 ` (2)` 区分，正文固定叫 `<标题>.md`。所以笔记自己的文件名恒等于标题，与我们造的容器无关。

> **后缀永不嵌套**：每次都从**原名**重新生成 ` (N)`，所以标题本来就叫 `报告 (2)` 也不会变成 `报告 (2) (2)`，只会顺延到 `报告 (3)`。
>
> **“不该发生”的情况只有一种姿势**：正文与 sidecar 走 `reserve()`（只登记不改名）、资源走 `allocate()`（可能改名），`buildZip()` 里还查一遍路径重复 —— 这三处都只可能由代码 bug 触发，统一按 `invariant()` 处理：**开发模式直接抛错、生产构建只记 `error`**。生产不抛是刻意的：导出是几分钟的长流程，抛错会让 `session.ts` 里那一圈 try/catch 把整份成果作废，代价与收益不匹配（见 `src/utils/invariant.ts`）。

### 1.5 任务队列、最小化与后台提醒

**为什么要把“任务”从对话框里拆出来**：对话框随时可能被收起，而导出本身要继续跑。所以任务活在 `src/export/session.ts` 里，视图只是订阅者 —— 完整对话框（`ui/export-dialog.ts`）与悬浮条（`ui/export-tasks.ts`）看的是同一份状态。

**任务状态机**：

```
scanning → ready → queued → running → done
（草稿）   （待导出） （排队）  （导出中）  （结束）
```

- 预检（`scanning`）在**任务创建时就跑**，只读本地、不阻塞任何东西；
- `ready` 之后点“开始导出”，任务进队列（`queued`）；
- 调度是**串行**的：`pump()` 发现没有正在跑的任务，才取队列里第一个开跑。同一时刻只跑一个，是因为请求节流本身就是按“串行调用”设计的（见 §十），并发只会把请求量叠上去；
- 结束时 `finish()` 把 `activeId` 清掉再 `pump()`，所以排队中的任务会自动接上。

**同一时刻只开一个对话框**：新对话框出现时，旧的那个如果还是草稿就直接丢弃，已经开跑的就收起成悬浮条。用户在笔记上再点一次“导出为 Markdown”，前一个任务的进度不会丢，只是换了个地方显示。

**对话框开着时，悬浮条整个藏起来**：它正好在对话框旁边，亮着只会抢注意力。实现是给遮罩**宿主**挂一个 class（`wze-dialog-open`，由 `ui/panel/host.ts` 的 `setExportDialogOpen()` 落上去），`panel.css` 里一条 `:host(.wze-dialog-open) .wze-taskbar { visibility: hidden; pointer-events: none }` 收工。

落这个 class 的时机是**对话框挂上时**与**收起动画跑完之后**（不是遮罩被摘掉的那一刻）—— 对话框收起的落点就是悬浮条，早一秒放出来，两者会同时亮着。放下 / 摘掉 class 的同时还会**广播**一次（`onExportDialogOpenChange`），因为悬浮条只是被 CSS 藏起来、收不到任何通知，它需要在“回到原处”的那一刻补一段出场（见下面“控件之间的接力”）。

为什么用 CSS、而不是让悬浮条自己判断“该不该显示”：

- 这纯粹是**显隐**，不涉及任务数据 —— 藏起来的只是那一层 DOM，**任务照跑，位置、展开状态、确认行都留在原地**，对话框一关就回到原处；
- 省掉了“开／关各通知一遍”的时序问题：那些路径里 `notifyTasks()` 的先后顺序并不都好使（`discardTask` 触发的那一轮，悬浮条会先于对话框渲染）；
- 藏起来的是 `visibility` 而不是 `display` —— **藏起来的东西仍然占着盒子**，`applyPosition()` 照跑（位置照样按新尺寸夹，缩过窗口也不会跑到视口外），接力锚点也照报。这一条是必须的，不能“优化”回 `display: none`：悬浮条常常是**在对话框还开着的时候**才建出来的（第一次把任务收进去），那一瞬间要是量不到盒子，对话框收起的落点就是空的，只能原地缩一下、指不出它收到哪儿去了。

代价是**那段时间够不着别的任务** —— 想换一个看，先在对话框里点 − 收起来（或直接关掉它）。这是明知的取舍；另一个选择是让悬浮条压在遮罩上方随时可点，但它会一直贴着对话框晃。**设置对话框不触发这条**（它跟悬浮条没有关系，开着时悬浮条照旧）。

**进度怎么算**（`session.ts` 的 `overallProgress()`）：

```
整体进度 = (已完成篇数 + 当前篇内部的比例) ÷ 总篇数        跑的过程中最多 99%
```

两个容易写错的地方：

- **不能写成 `index / total`**：`index` 是“正在处理第几篇”，不是“处理完几篇”。那样一共 3 篇、刚开始处理第 3 篇时进度条就已经满了 —— 和“还有一篇没导完”是矛盾的。`index - 1 + within` 才是真正做完的量；
- **`within` 必须“干完一步才涨”**：一篇笔记的工作量算作“正文处理 1 步 + 要下载的图片数 + 要下载的附件数”，`task.ts` 里每完成一步上报一次 `noteProgress`（0..1，见 `ExportProgress.noteProgress`）。所以只有一篇、但有 10 张图时，进度条不会在 0% 干等，也不会一步跳到 100%；
- 99% 是刻意的上限：**满格只留给任务真的结束那一刻**（`applyOutcome()` 里写 100）。被中止的任务则保留停下时的位置 —— 那是有信息量的。

**逐篇结果“结束即落地”**（`task.ts` 的 `onNoteDone` → `session.ts` 的 `applyNoteDone()`）：一篇跑完（成功 / 失败 / 跳过）立刻把它那一行从“导出中…”换成真正的结论。别改回“等整批结束再一次性刷（只在 `applyOutcome()` 里写行）”——那样已经导完的行会一直挂着“导出中…”，**同一屏里会出现两行都写着“导出中…”**（刚导完的那行 + 正在导的那行），用户分不清哪篇在跑，几百篇时列表看着就像卡住了。两处用的是同一个 `applyResultToRow()`（它每次都先清 `problems` 再重建，所以同一个结果应用两次是幂等的，收尾那一次不会写成双份）。被中止打断的那一篇**没有**结果，由 `applyOutcome()` 统一记成“已中止，未处理”。

**左栏两个页签（笔记 / 问题）各自记住滚动位置**（`task.listScroll: { all, issues }`，和 `tab` 一样挂在 `session.ts` 的任务上）。列表重建时浏览器只负责把 `scrollTop` 夹进新内容的范围，不会替我们记住“看到哪儿了”，所以视图自己接住，按两种意图分开（`ui/export-dialog.ts` 的 `renderList()`）：

- **换页签**：落回那一页自己的存档 —— 在“笔记”翻到第 200 篇看进度、切去“问题”再切回来，位置还在；
- **同一页签但条目变了**（导出中问题页在长）：按**行锚定** —— 让重建前视口顶部那一行在重建后停在原处，新条目插在它上面也不会把视口内容顶走；
- **收起再打开**：从悬浮条点回来时同样还原 —— 这正是位置必须存**任务**上、不能只留在对话框里的原因（收起会摘掉整棵 DOM）。写入点只有两个：列表重建前、以及 `closeDialog()`。

不做的话实测就是这样：切到“问题”页基本必然回顶（问题通常只有几行、比视口矮，`scrollTop` 直接被夹成 0），再切回“笔记”也就在顶部了；收起后重开更是一定从第一行开始。

> ⚠️ **首次渲染时列表是刚建出来的，`scrollTop` 恒为 0** —— 那一刻不能把它存回去，否则每次重开都会用 0 抹掉上次记住的位置（实测踩过，用一个 `renderedOnce` 标志挡掉）。

**扫描期（`scanning`）用不确定进度条**：那一段才刚刚开始读本地内容，拿不出“第几篇 / 共几篇”之外的量，而预检的篇数已经在右栏摘要里了（`summarize()`），所以底部不报百分比，改由 `panel.css` 的 `.wze-export-bar-indeterminate` 让一条窄条来回走 —— 一条永远不动的空槽和“卡住了”长得一模一样，而预检恰恰是最像没反应的那一段。宽度由 CSS 给（`export-dialog.ts` 会把内联宽度撤掉，内联盖得过规则），`--wze-dur-loop` 是它的时长；`prefers-reduced-motion` 下循环整个去掉，换成一条静止的浅色满条（0ms + `infinite` 会停在最后一帧 = 条子跑出屏幕，看着就是空的）。

> 这条**不是**“把进度条改成跑马灯”的许可证：只有扫描期这样，`running` 期间仍然是确定进度（上一条的公式），满格仍然只留给结束。

**悬浮条**（默认右下角）显示所有“已开始 + 对话框没收着它”的任务。版面是**一套槽位、两种形态**：

```
┌────────────────────────────────┐
│              ────              │  把手条（18px）：唯一的拖拽面，两种形态都在
├────────────────────────────────┤
│ 导出任务 2 个 · 1 个进行中   ⌄ │  分组行（仅多任务）：整行可点 = 展开 / 折叠
├────────────────────────────────┤
│ 导出中   正在处理 2/5 · 标题    │  任务行：点它打开对话框
│ [中止]                         │
│ ▓▓▓▓░░░░░░░░░░░░░░░░░░░░       │
└────────────────────────────────┘
```

| 情况 | 形态 |
| --- | --- |
| 只有一个任务 | 把手条 + 一行任务行（状态 / 进度条 / 随状态变的按钮） |
| 多个任务 | 把手条 + 分组行 + （折叠时）一行汇总 / （展开时）逐条任务行 |

多任务合并是照着通知栏“同类通知合成一组”的做法（任务一多，一叠卡片会糊住半个屏幕）。汇总取的是**正在跑的那个任务**（没有就取排队中、再没有就取最后一个），带一条总体进度条。重新出现分组时回到折叠态，别记住上一轮的手气。

单任务**不**也摆一条带文字的标题栏：它没有第二层内容可概括，那行文字只会是任务行状态词的复述，却要给最常见的形态多付一条常驻高度。统一的是**槽位与手势**，不是内容。

**一个像素只承诺一个手势**（这份 UI 最重要的一条约束）：

| 区域 | 手势 | 信号 |
| --- | --- | --- |
| 把手条 | 拖动 | 居中的把手 + `cursor: grab` + tooltip |
| 分组行 | 展开 / 折叠 | hover 底色 + 箭头随 hover 加深 + `aria-expanded` |
| 汇总行 | 展开任务列表 | hover 底色 + 整行可聚焦 |
| 任务行 | 打开对话框 | hover 底色 + tooltip + 整行可聚焦 |
| 行内按钮 | 各自的动作 | 按钮形状 + tooltip 说明后果（尤其“关闭”会把没下载的文件一起放掉） |

四者互不重叠，所以**“拖拽之后紧跟的那次 click”不需要任何拦截**：它只会落在没有监听器的地方。反过来，只要拖拽面和可点元素重叠，就得靠 pointer capture / 吞 click / 渲染不重建这类机制去救 —— 全是踩过的坑（见下面第 3 条）。

键盘上是同一张图：拖动没有键盘等价物（退路是双击把手，见下），其余三处都可聚焦，`Enter` 与 `Space` 等价于点击，焦点圈在 `panel.css` 的 `.wze-task:focus-visible` / `.wze-task-summary:focus-visible`。三个整行可点的角色**各不相同，别拉平**：

| 行 | 角色 | 为什么 |
| --- | --- | --- |
| 分组行 / 汇总行 | `role="button"` | 都是叶子：里面只有文字、箭头、进度条 |
| 任务行 | `role="group"` + `aria-label="打开导出详情"` | 行里还装着“中止 / 下载 / 关闭”与确认行的两个按钮。`button` 的子节点在无障碍树里会被当作纯装饰（children presentational），那么写会让它们**从读屏里消失** —— 其中就包括“关闭会把没下载的文件一起放掉”那道确认。`group` 只把这一行标成一个带名字的组，里面的控件照旧可见、可聚焦 |

任务行的 `keydown` 还挡了一道：焦点在行内按钮（含确认行）上时，冒上来的 `Enter` 归它们自己（回车 = 点那个按钮），只有焦点真的在这一行自己身上时才打开对话框。汇总行的 `aria-expanded` 恒为 `false` —— 展开之后它自己就被 `hidden` 掉了，看得见它的时候一定是收起态。

**焦点跟着这一行走**：键盘用户从某一行按 `Enter` 打开对话框、再收起（Esc / −）时，焦点要回到**同一个任务的那一行**上 —— 而那一行在对话框期间被拆掉了，重建的是新节点（`ui/export-tasks.ts` 的 `rememberRowFocus()` / `restoreRowFocus()`，规则见 §1.2 末尾那条注）。若不接管，焦点会掉在 `body` 上，用户得从宿主页面从头 Tab 回来（悬浮条在 `body` 末尾，是整页最后一段 Tab 顺序）。只在**焦点确实没处可去**时才接管：用户已经用鼠标点去别处就不该抢回来。

**高度露出 / 收起的动画**（`ui/kit/morph.ts` 的 `setRevealed()`，三处共用）：`hidden` 是瞬时开关，做不了补间，所以自己量高度再跑一段 WAAPI —— 露出 = 0 → 自然高度，收起 = 当前高度 → 0，跑完再落回 `hidden`（结束时节点真的不在布局里，键盘与读屏都到不了，跟没写动画时一致）。三个消费者：

| 用在哪 | 节点 |
| --- | --- |
| 悬浮条展开 / 折叠任务明细 | `.wze-task-summary` / `.wze-task-list` |
| **确认行露头 / 收起** | `.wze-confirm`（`ui/kit/confirm.ts`，模态内外共用） |

- 只在**形态真的变了**的时候补一次：`render()` 每次进度刷新都会跑（60ms 一次），不拦一道就变成幻灯片；
- 连点两次也能接上：打断上一次之前先量它当前的**动画高度**，再从那儿继续；
- 箭头同时转 180°（CSS `transition`，与高度补间**读同一份 token**：`--wze-dur-reveal` / `--wze-ease`，两者一起动才像同一件事）；
- **只在补间期间裁剪**（临时 `overflow: hidden`，跑完还回去）—— 常驻的 `overflow: hidden` 会把里面按钮的焦点圈沿边切掉一条；
- 尊重 `prefers-reduced-motion`：那种情况下时长为 0，直接落定。

> ⚠️ 两个细节：
>
> 1. **箭头画的是“朝上”的那一个**：悬浮条贴着屏幕下沿，展开是**往上长**，所以收起态朝上（暗示点它会往上展开）、展开后转 180° 朝下。别按“收起=朝下”的通用直觉改回去；
> 2. **被补间的节点不能带 padding / margin**：`box-sizing: border-box` 下 `height` 压不过 padding —— 间距要是留在被补间的那一层，动画只能长到“padding 的厚度”就停住；`margin` 更彻底，它压根不在 `height` 里，会在动画开始的一瞬间先跳出来。所以间距一律留在内层：汇总行是 `.wze-task-summary-inner`，确认行是 `.wze-confirm-inner`（外层的 `padding` / `margin` 全空着，只负责被补间的高度）。实测过：确认行原来是 `.wze-task .wze-confirm { margin-top: 8px }`，点“关闭”时卡片会先猛长 8px 再慢慢长剩下的。

**悬浮条与对话框之间的接力**（`ui/kit/morph.ts`）：从悬浮条点开对话框、再把对话框收起成悬浮条，这两下要能看出是**同一个东西换了地方**，而不是两个控件各自被开关了一次。做法是 FLIP 加一个**锚点矩形**：进场 = 从锚点长出来，退场 = 收成锚点，尺寸不一样时 `scale` 的 x / y 各算各的（那份“变形”正是在指认它收到了哪儿去）。

- 锚点是**悬浮条最后落位时的盒子**：由 `export-tasks.ts` 的 `applyPosition()` 每次落 DOM 时报一次（对话框把它藏起来的那段时间**照样报** —— 藏着只是不画，盒子还在，见上文，所以落点永远是它此刻的样子）。对接的两个模块（`export-tasks` / `export-dialog`）本来就有 import 关系（后者被前者用 `openTaskDialog` 调），所以锚点放在 `kit/morph.ts` 里由双方读写，不再添一条模块环；
- 报的是**落定的盒子**（右 / 下偏移 + `offsetWidth` / `offsetHeight`），不是 `getBoundingClientRect()` —— 后者**含**正在跑的补间那层 `transform`，动画途中量到的是“半路的样子”，拿去当锚点会让对话框从半空中长出来。`applyPosition()` / `setPosition()` 夹位置同理，一律只认布局尺寸；
- 整条悬浮条没了（`teardown()`）才把锚点清成 `null`；
- ⚠️ **顺序是配方的一部分**：最小化必须**先把任务交给悬浮条**（`notifyTasks()` 让它就位、报出落点），**再**收起对话框（`closeDialog(getBarAnchor())`）。第一次把任务收进去时悬浮条是这一刻才被建出来的，反过来写锚点就是空的 —— 症状是收起动画只会原地缩一下、指不出收到哪儿去，而且只在“屏幕上还没有悬浮条”时出现（合并版悬浮条早就在了，所以看着一直是好的）；
- **入场**：对话框从锚点长出来（`createModal({ origin })`）。补间在遮罩挂上的**下一帧**才开始量、开始跑 —— 内容由调用方在同一个任务里同步填进插槽，早一帧量到的是空壳的尺寸；在那之前遮罩先 `opacity: 0` 藏着，所以不会先露一帧原样；
- **退场**：最小化给锚点（收向悬浮条），草稿取消 / 结束后关闭给 `null`（原地缩小淡出）。“回哪儿去”和“有没有地方可回”是两件事 —— 被销毁的东西没有去处，收向悬浮条反而像“它还在那边等着”；
- 收完之后才摘 `wze-dialog-open`（见上文），悬浮条随即在原处冒出来：一个收进去、一个冒出来，中间不断。悬浮条自己出现 / 消失也补一段（出场淡入 + 缩放；任务全结束是**先收再摘 DOM**）；
- 全都要**尊重 `prefers-reduced-motion`**：那种情况下时长为 0，所有动作瞬时落定（和展开 / 折叠同一套规则）。

**动效 token（时长与曲线只有一处）**：`--wze-dur-fast` / `--wze-dur-reveal` / `--wze-dur-normal` / `--wze-dur-fly` 与 `--wze-ease` 定义在 `src/style.css` 的 `:root`。`panel.css` 里的 `transition` 直接 `var()` 用；`ui/kit/morph.ts` 的 WAAPI 补间由 `motionMs()` / `motionEase()` 读出来喂进去（首次用到时读一次、带缓存；`--wze-dur-fly` 是双击把手飞回原位那一段，`--wze-dur-normal` 同时也是 toast 摘节点的延迟）。

从前是 JS 一套常量、CSS 另一套（`0.15s` / `0.16s` / `0.2s` 各写各的，长短关系只靠注释提醒“改一处要连着另一处改”），折叠箭头那条甚至专门注释过这一点 —— 现在手感只改一处。`prefers-reduced-motion` 也在 **token 层**表达：`style.css` 里把四个时长都归零，CSS 的 `transition` 与 JS 的补间于是同时归零，各处“时长为 0 就瞬时落定”的短路判断照旧有效，`panel.css` 里那条只关折叠箭头的媒体查询因此删掉了。代价是判定成了**加载时快照**：会话中途改系统设置，CSS 侧（媒体查询）立刻跟上，JS 侧要刷新才跟上 —— 差的就是补间多跑或少跑两百毫秒，不影响任何状态。

**拖动改位置**：只有把手条是拖拽面，位移超过 4px 才算拖拽（手抖不该把悬浮条挪走）。松手把位置写进设置（`exportBarPos`），下次直接落在老地方。拖动没有键盘等价物，所以另留一条退路：**双击把手条飞回右下角**（同时清掉 `exportBarPos`），设置里的“重置脚本设置”也会清。那一下是那段位移补间：先按默认位置落 DOM（改位置只有 `setPosition()` 一处），再从原位置补动画 —— 逻辑位置在动画开始前就已经是终点了，所以跑到一半被打断也不会留下半路的状态。飞行途中按住把手不要紧：真正开始拖的那一刻才把这段补间落定，并按落定造成的视觉位移校正拖拽起点（`grabShift()`），拖起来不跳。

**位置是“请求值 + 每次重夹”两件事**（`position` / `applyPosition()`）：`position` 只记用户拖到哪儿，落 DOM 时再按**当前尺寸**夹一次（贴边留 `EDGE_GAP`）。夹取必须放在落 DOM 这一步、而不是只在拖拽那一刻做 —— 悬浮条锚的是**下沿**，卡片长高（展开明细、任务变多、确认行亮起）是**往上长**，而拖拽可能发生在这张卡片还矮的时候：

> ⚠️ **实测踩过**：把收起的悬浮条拖到屏幕最上沿，再展开明细，卡片往上长得比 `bottom` 留的余量多，顶部那条**把手条（唯一的拖拽面）被顶出视口**，用户再也拖不回来、只能靠双击复位（而那也得先摸得到把手条）。所以高度一变就重夹：`ResizeObserver` 盯着卡片，**每次高度变化**（含展开那 160ms 逐帧长高的过程）都重跑一次 `applyPosition()`，卡片沿着上边界“滑下来”，把手条始终留在视口里。窗口 resize 同理。

重夹只改“显示在哪儿”，不动 `position` —— 收起之后它会自己回到用户拖到的那个高度。

行节点按任务 id 复用，进度刷新只改文字与宽度，不重建 DOM —— 除了下面第 3 条说的点击问题，每 60ms 重建一次也会把按钮的 hover 反复打断。

> ⚠️ 三个踩过的坑，改之前先读：
>
> 1. **阴影不能挂在会被滚动裁剪的子元素上。** 任务列表需要 `overflow-y: auto`，而任何非 `visible` 的 overflow 都会在**自己的 padding box** 处裁剪子元素 —— 卡片自己的 `box-shadow` 画在卡片外面，于是被容器切出一条直边，看起来像“阴影被一个矩形框裁掉了”。现在的做法是：阴影只挂在外壳 `.wze-task-shell` 上（它自己不裁剪，`overflow: hidden` 只用来把内容切进圆角，**裁不到自己的阴影**），里面每一行都是扁平的（hover 底色 + 分隔线，零阴影），顺带也更像“一组的通知”而不是一叠卡片；
> 2. **`z-index` 高于模态遮罩**：另一个任务的对话框开着时，这里的任务仍然要看得到、点得到。宿主 `:host` 是 `pointer-events: none`，所以 `.wze-taskbar` 必须自己打开 `pointer-events: auto`。另外 `cursor` 是**继承属性**，`grab` 只放在把手条上（`.wze-task-titlebar`），别放到容器上 —— 否则里面的按钮会跟着变抓手，还得逐个写回 `cursor: default`；
> 3. **⚠️ 点击要活下来，`mousedown` 到 `mouseup` 之间就不能动 DOM。** 这条踩了两次，症状都是“悬浮条怎么点都打不开对话框”。浏览器判定一次 click 的目标时，用的是按下与松开两次命中的共同祖先，所以任何在中间把节点换掉的动作都会让点击落到祖先（外壳）上，而真正挂了监听的元素永远收不到：
>    - **不要用 `setPointerCapture`**：实测（Chrome 154）在某个元素上捕获指针之后，后续的 `pointerup` 与 `click` 会被**一并改判给捕获元素**。之前捕获在外壳上，`click.target` 就变成了外壳本身。现在拖拽改成在 `window` 上听 move / up，走原生命中测试；
>    - **不要在每次渲染都 `replaceChildren`**：进度每 60ms 刷新一次，把已有节点“摘下来再插回去”同样会让点击易主。行只在集合/顺序真的变了时才动 DOM（内容刷新走 `updateRow`），按钮只在集合变了时才重建（`data-actions` 记着上一次的按钮列表）。
>
>   顺带一提：这三条里唯一能被“设计掉”的是**共享表面**——把手势拆到互不重叠的槽位之后，拖拽不再和任何点击抢像素（上面那张表）。剩下两条是机制层面的，拆槽位也躲不掉。
>
> 这类问题**合成事件验不出来**（`el.click()` 不经过命中测试），必须用真实鼠标事件点一遍 —— 做法见 [ai-debugging.md §六](ai-debugging.md)。

**关页面守卫**：只要有 `queued` / `running` 的任务，就给 `window` 挂 `beforeunload`（`preventDefault()` + `returnValue`），刷新或关闭页面时由浏览器弹原生确认。文案归浏览器管，我们能决定的只有“拦不拦”。任务全结束后不再拦。

**完成提醒**（`ui/notify.ts`）：任务跑完时，如果对话框是收起的**或**页面在后台（`document.hidden`），发一条系统通知；对话框就摆在眼前、页面也可见时什么都不做（结果已经在屏幕上，再弹一次是打扰）。通知优先走 `GM_notification`（不需要页面授权、页面最小化也能弹），退而用 `Notification`，都不可用时降级成页面内 toast。点通知会把对话框叫回来。

**这一层的边界**：导出全在页面里跑，**没有任何自建的持久化 worker**。所以 SPA 内切笔记、切知识库都不影响（内容是按 `docGuid` 从虚拟域 / IndexedDB / `LiveEditor` 取的，不依赖“当前打开哪篇”），但刷新、关标签页、离开 `wiz.cn/xapp` 都会让任务戛然而止 —— 那份 `beforeunload` 确认就是为此。

### 1.6 危险动作只走一条确认行

会丢东西的动作有**四个**入口，**交互契约完全一样**，因此必须是同一个控件、同一套文案：

| 入口 | 会掉什么 |
| --- | --- |
| 导出对话框底部“中止”（导出中） | 当前这一篇（整个作废，§1.7）+ 还没处理的那几十篇 |
| 导出对话框底部“关闭”（已结束） | 这批导出记录 + 那份 Blob（§1.1） |
| 设置对话框底部“重置脚本设置” | 改过的开关一起回默认 |
| 悬浮条任务行上的“中止”/“关闭” | 同上两件事，只是入口在悬浮条上（“关闭”那句说的是“从悬浮条移除”） |

> 入口数（4）比消费者文件数（3）多一个：导出对话框与悬浮条各有**两条**确认行（中止、关闭）。
> 一个决策一条 —— 两条的后果、执行按钮、不做按钮都不一样，合并成一条复用得把控件改成
> “谁最后打开的算谁的”，那正是本节要避免的隐性规则。两者天然互斥（中止只在跑着时有意义、
> 关闭只在结束之后），所以屏幕上任何时刻最多只有一条露着头。

实现是 `src/ui/kit/confirm.ts`（`createConfirmRow`），位置各有各的落点：模态里挂 `ModalHandle.notice`（按钮行**正上方**），悬浮条里挂进任务卡片。**不是模态、也不是“按钮变色”**，理由依次是：

1. **说清后果要一整句**。“关闭会清掉这批导出记录和已生成的文件，还没下载的话，先下载再关”塞不进按钮文案；而“再点一次确认重置”那种写法其实什么都没说（本节第一版就是它，已废弃）。
2. **位置必须贴着触发它的按钮**。点的是底部按钮，反馈就不能出现在屏幕另一头 —— 这也是**顶部横幅与底部确认行分开成两个槽**的原因：横幅放通知（“需要刷新”、导出那句“可以点右上角 − 收起”），与具体按钮无关；确认行绑触发按钮。两者可以同时出现，谁也不用让位（第一版共用一条带子，还得写一条互斥规则）。
3. **不做超时自动收起**。确认行是显式状态、自己带“不做”出口；`setTimeout` 复位是用户看不见的隐性规则，只配留给无副作用的小动作。

行为契约（三处一致，别再各自实现）：

| 事项 | 规则 |
| --- | --- |
| 文案 | 说明用**陈述句**；执行按钮是“动词 + 对象”；不做按钮是这个动作“不做”的说法（“继续查看”“暂不重置”“继续留着”），**不用泛化的“取消/确定”**（“取消”在导出对话框里早有别的含义） |
| 位置 | 不做在左、执行在右；执行按钮**独占危险色**（`.wze-btn-danger`），触发按钮自己不变色 —— 全站“红色 = 这一下真的执行” |
| 触发按钮 | 待决期间它**不可用**：挂 `aria-disabled="true"`、并且**交还 hover 底色**（外观与原生 `:disabled` 共用一套，见 `panel.css`）。动作被挂起时就不该看起来还能点 —— 但也不让它消失（它得留在原地当焦点回收的落点），更不拿它当“再点一次就执行”的开关（那套早已废弃，见本节开头） |
| 焦点 | 展开时焦点给**不做**那个按钮（键盘回车不会误执行）；收起时还给触发按钮（`aria-disabled` 仍然可聚焦，`disabled` 就不行了 —— 这也是不用 `disabled` 的原因之一）；确认路径不还（按钮马上就被移除了） |
| Esc | **只收起它**，不关对话框、不最小化。模态里由调用方代接（模态壳在 `document` 捕获阶段 `stopPropagation()`，控件自己收不到，所以 `onDismiss` 里先问一句 `isOpen()`）；不在模态里（悬浮条）时控件自己接 —— 焦点本来就在行内（打开时给了“不做”），事件会冒泡上来 |
| 阶段变化 | 触发按钮没了就没意义了：**每条行只在自己那个阶段里有意义**（中止 = 跑着、关闭 = 结束），离开就 `.close()` —— 对话框在 `render()` 里判（`phase !== 'running'` / `phase !== 'done'`）、悬浮条在 `updateRow()` 里做同样的事。⚠️ 顺序：**先 `close()`（顺带解禁旧按钮节点）再重建按钮** |
| 点击 | 控件整块吞掉 click。悬浮条的任务卡片是“点一下打开对话框”的热区，不吞就会顺带把对话框也打开 |
| 无障碍 | 说明用 `aria-describedby` 挂到两个按钮上；展开期间触发按钮带 `aria-controls`（指向那条行）——**不是 `aria-expanded`**，那个的语义是“再激活一次会收起”，而它此刻既不可用也没这条行为 |
| 露头 / 收起 | 走 `kit/morph.ts` 的 `setRevealed()`（0 ↔ 自然高度）：它总是从某个容器的底边长出来，瞬闪一下等于整块界面凭空变高（悬浮条里就是卡片猛地长一截）。因此外层 `.wze-confirm` 只负责被补间的高度、**不带 padding / margin**，间距与内边距都在内层 `.wze-confirm-inner`（见 §1.5） |

`ModalHandle.notice` 这个槽**由调用方维护 `hidden` 吗？不用** —— `.wze-modal-notice:has(> :not([hidden]))` 自己判断有没有可见内容，否则“控件自己开合 + 插槽另存一份状态”迟早漏一处。那个槽自己**没有 padding**（都挪进确认行的内层了），所以行一露头，整块是跟着它一起长出来的。`:has()` 不可用的浏览器只是少一条分隔线与一层底色，功能不受影响。

> ⚠️ 那两处“不可用 / 关系”的标记是挂在触发按钮**节点**上的，确认行亮着的时候别把那个节点换掉。悬浮条那套“按钮只在集合真的变了时才 `replaceChildren`”的规则正好也守住了这里，但顺序得对：阶段一变要先 `close()` 确认行（顺带解禁旧节点）、再换按钮，反过来新按钮就不带标记了 —— 行亮着、按钮却看起来能点。

### 1.7 中止：一条信号贯穿到底

点“中止”会先过一次确认行（§1.2：那一步丢掉的是还没处理的那几十篇），**确认的只是“要不要中止”**，
确认之后的事才是这一节：中止不是把某个循环标志置上就算了 —— 一条 `AbortSignal` 从会话层贯穿到每一次 `fetch`：
`session.ts` 的 `activeAbort` → `task.ts` 的 `hooks.signal` → `note-content.ts` → `app-bridge.ts` → `request`。
这样喊停之后：

- **在飞的请求立刻作废**，不必等它超时，也不必等这一张图下完；
- **正在渲染的那一篇整个作废**：既不算失败也不算跳过（它什么都还没落进产物，结果页里记成“已中止，未处理”）。中止打断的那一步带回来的“取不到正文 / 取不到评论”只是中止的副作用，**不能**当成本篇自己的结论 —— 否则结果页会凭空多出几条“跳过”；
- 已经落进产物的（正文 + 已下好的图片 / 附件）照旧保留，见 §1.1 的“下载已完成部分”。

三处容易写错：

1. **中止只有一条通道**：不要再在任务上挂一个 `cancelRequested` 之类的标志。两个真相源迟早不同步（请求被 abort 了、标志却没置上），判定一律用 `signal.aborted`；
2. **不可中止的等待要显式收口**：应用的 `syncOfflineDoc`（协作笔记联网同步）只给超时、没有取消接口（默认 8s），所以要用 `utils/abort.ts` 的 `raceAbort()` 把它纳入这条通道 —— 中止后不再等它，那条只读同步自己在后台跑完（写的是本地缓存，没有副作用）；
3. **节流与重试的等待（§十）也要能被中止打断**：`app-bridge` 的 `sleep()` 与 `attemptCandidates()` 都接了 `signal`，否则一次中止最多还要多等一个间隔（乃至一次 400ms 的退避）。

### 1.8 收尾打包：让出主线程 + 报进度

中止之后（以及每次正常结束时）都要把已收集的内容打成 zip。这一段是**纯 CPU 的同步活**，几百篇带图片时能占住主线程好几秒 —— 以前它的表现就是“点了中止之后界面完全冻住，连文案都不动”。

`archive.ts` 的 `buildZip()` 因此是**流式**的（fflate 的 `Zip` + `ZipDeflate` / `ZipPassThrough`，逐文件写），而不是一次性的 `zipSync`：

- 每写完一个文件都有机会**让出主线程一帧**。让出用 `MessageChannel`，**不能用 `setTimeout` / `requestAnimationFrame`** —— 后台标签页里前者会被节流到 1s 一次（藏久了还会更狠）、后者干脆不触发，那等于把打包挂住；
- 打包期间持续上报 `onPackaging`，底部与悬浮条那行字变成“正在打包已完成的部分 120/340…”；**进度条不动**（按 §1.5 的约定：跑的过程中最多 99%，满格只留给任务结束）；
- **已经压过的格式直接存储**（`STORED_EXTENSIONS`：png / jpg / pdf / zip / docx / mp4 / woff2…），不再白烧 CPU 去做几乎压不小的 deflate —— 产物里的字节大头就是它们，这也是打包耗时的主要来源。代价是这些条目按原大小落盘（zip 比之前略大一点，换掉的是几秒的无用功）；
- 流式写法会给每个条目加一段标准的 data descriptor（每条约 +16 字节），任何解压工具都能正常打开；
- **收尾那一步直接把分片数组交给 `new Blob(chunks)`**，别先 `concat` 也别 `.map(toArrayBuffer)` —— 那两种写法都会在渲染进程里再抄一份完整的 zip（每片 `slice()` 一遍，几百 MB 的导出里就是几百 MB）。Blob 的字节进的是浏览器的 blob storage（Chrome 大对象会落到磁盘），不占 JS 堆；内存峰值那一段见 §1.9；
- 打包**不可中止**（不再吃第二个信号）：第二个“中止”若把它掐掉，等于手一抖就把已经下好的图片全丢。中止只承诺“不再往下导”，已完成的部分一定打给你。

**让出粒度止步于“一个文件”**：`file.push()` 是一整块同步活（CRC + deflate），一个几百 MB 的附件仍会占满一格。真要切碎，fflate 支持分次 push（`push(slice, false)` … `push(rest, true)`），记在 §十二。

**篇内也要让出**（同一个原语，`src/utils/yield.ts`）：单篇的转换同样是一串同步 CPU 活 —— 宿主自己的 `html2Doc` / `doc2markdown`（**搬不进 Worker**：函数不可 transfer、还依赖页面环境）、`DOMParser` 解析、一遍遍全篇 regex（`unescapeMarkdown`、`rewriteImageTargets`、`sanitizeNoteHtml`、`localizeHtmlResources`）、`TextEncoder` 编码。它们的开销只跟**这一篇**的大小走（篇与篇之间有 await，主线程能呼吸），所以普通笔记无感，几十 MB 的剪藏会顿一下 —— 于是在这些步骤**之间**插 `await breathe()`（`renderNote` 里那串“一步一让”的写法，别合并相邻几步，合并就把让出点吃掉了）；打包与篇内共用 `createYielder()`：**只在连续占用主线程 ≥ 16ms 之后才真的让**，小笔记一次都不让，不为此付几百次的 macrotask 开销。

### 1.9 产物放在哪、峰值占多少内存

导出结果**在下载之前一直留着**（§1.1），形态是一个 **`Blob`**，不是字节数组：

| 阶段 | 谁拿着 | 占用 |
| --- | --- | --- |
| 导出过程中 | `task.ts` 的 `entries[]`：**每篇正文 + 每一张已下到的图片 / 附件的原始字节** | R（所有原始字节之和），活到打包结束 |
| 收尾打包 | `archive.ts` 的 `chunks[]`（fflate 流式产出的 zip 分片） | Z（zip 体积）—— 但见下面那条：**它引用的是同一批字节，不是第二份** |
| 结束之后 | `ExportTask.file = { blob, filename }` | Z —— 字节在**浏览器的 blob storage** 里，不在 JS 堆（Chrome 大到一定程度会落到磁盘） |

所以“内存”要分两层看，别混着算。实测（2026-10-07，调试浏览器，`performance.memory.usedJSHeapSize`）：一块 96 MB 的 `ArrayBuffer` 计入 +96 MB；而 `new Blob([view])` 与 `new Blob([buffer])` **都不再涨** —— Blob 的字节确实出了 JS 堆。同一份 `Uint8Array` 若用 `map(toArrayBuffer)` 转一遍再塞进 Blob，才会实实在在地多出一份（这就是 §1.8 里“别 concat / 别 map”的由来）。

⚠️ **stored 条目是“引用转发”，不是复制**（`ZipPassThrough.process` 直接把块的引用交给 sink，fflate 的 `Zip` 又原样推进 `chunks`）。所以：

- **渲染进程峰值 ≈ R，不是 R + Z**：图片/附件的那些 `Uint8Array` 既挂在 `entries` 里、也被 `chunks` 引用着（同一块内存，两个引用），只有正文与 `.svg` 是“原始 + 压缩后”两份（正文小，忽略）；
- **“边导边写、随即释放”省不掉图片的内存**：省下的只有走 deflate 的正文原始字节（几百篇也就几十 MB）—— 想做这个优化前先想清楚这条，别白改一遍；
- 真想降峰值，只能让**输出离开渲染进程**：把 zip 分片边生成边写进磁盘（OPFS 的 `createWritable()`，或 File System Access 的 `showSaveFilePicker()`），峰值才能从 R 掉到“≈ 单篇”。代价是要用户手势先选保存位置、且 Chromium 之外没有 picker（OPFS 更广但要自己拼下载）；
- 把打包挪进 Worker **不降内存**（R/Z 只是换个堆），它只解决“卡住”，而那个已经用让出主线程解决了（§1.8）。

量级（按公式推，不是实测）：纯文本几百篇 → R 几十 MB，没有压力；上千篇**带图**的（假定图片合计 300 MB）→ 渲染进程峰值 ≈ 0.3 GB，外加浏览器侧 blob storage 里约 0.3 GB（大概率落盘）。这份 Blob 要等任务被关闭（`discardTask()`）才释放 —— **连着导两次、前一个不收起来，浏览器侧就是两份**；`再次导出`覆盖的是自己那一份。

在对话框里选择，会被记住（存在 GM 存储里）。

| 选项 | 默认 | 说明 |

| 包含评论 | 开 | 在正文末尾追加“评论”章节，见 §3.3 |
| 允许联网补全本地没有的笔记 | 开 | 见 §五 |
| 导出笔记元数据 | 开 | 见 §八 |
| └ 元数据形态 | YAML front matter | 或“同名 `.meta.json`” |
| └ 附带 WizNote 原始字段 | 关 | `docGuid` / 原始 `type` 等，供排查 |

> **改默认值只影响“从未动过这个开关”的用户。** 这些开关每次导出开始都会被写回存储，所以只要用过一次导出，存储里就有值了 —— 老用户的手动选择**一律不动**（不覆盖用户已有配置）。想让某台机器回到新默认，删掉存储里的对应键（如 `exportKeepComments`）即可。

### 3.1 同时导出 HTML（保真备份）

默认关闭。勾选后，**走“HTML → doc → markdown”这条有损路径**的笔记会多产出一份同名 `.html`：

| 笔记类型 | md | 另附 html |
| --- | --- | --- |
| 普通笔记 / 旧版 Markdown 笔记 | ✓ | ✓（源就是 HTML） |
| Lite Markdown 笔记 | ✓ | ✗（md 是从 `<pre>` 取的原文，已经无损） |
| 协作笔记 | ✓ | ✗（源是 doc JSON；它的 `index.html` 只有占位页） |
| 大纲笔记 | ✓ | ✓（md 是从 HTML 的 `div.node` 树反推的，见 [note-types.md § 五](note-types.md)） |
| 手写 / 公式 | ✗ | ✗（产物本身就是 html，不重复产出） |

判断标准就一句话：**只有内容是从 HTML 反推出来的，HTML 才有备份价值**。（这条规则的由来见 [site-internals.md § 六](site-internals.md#六转换链路html2doc--doc2markdown)。）

> ⚠️ 写出的 HTML 同样要过 `sanitizeNoteHtml()` —— 否则也会带上 `body { opacity: 0 }` 与 `/wizDocument/*.js` 那套脚手架，双击打开就是一片空白。实测确认：导出后 `opacity:0` 为 `false`、外链 script 数为 0、正文完整。

sidecar 里的图片引用也会一并本地化（改写成 `images/<文件名>`，与 markdown 共用同一份图），否则离线打开会缺图 —— 见 §4.3。附件链接同理：`wiz://open_attachment` 会指向 `attachments/<文件名>`（见 §4.6）。

### 3.2 不支持的类型的 HTML 兜底：必须剥掉编辑器脚手架

手写 / 旧版公式笔记导出的是原始 HTML。但笔记 HTML 里夹着应用注入的 **编辑器脚手架**，直接导出会“打不开”：

```html
<style id="note-loading" name="wiz_unsave_style">body { opacity: 0 }</style>
<script wiz_style="unsave" src="/wizDocument/index.js"></script>
```

`body` 被设成完全透明，要靠编辑器 JS 加载后才恢复；而那个 JS 是**绝对路径**，`file://` 打开必然 404 → **一片空白**（内容其实都在文件里）。

这些元素带 `wiz_style="unsave"` / `name="wiz_unsave_style"` 标记，是应用自己的约定（应用保存笔记时也会跳过它们），所以导出前用 `sanitizeNoteHtml()` 剥掉。实测（当时是拿大纲笔记的 HTML 测的，手写 / 公式的脚手架同类）：`body` 的 `opacity` 从 `0` 变 `1`，正文节点数不变（76 → 76），外部 script 归零，原笔记的样式规则保留。

### 3.3 包含评论：正文末尾追加“评论”章节

**默认开启**（2026-10-04 从关闭改成开启）。勾选后，评论以**独立章节**追加在正文末尾：

```md
…正文最后一段…

---

# 评论（1 条）

**作者** · 2026-10-03 22:53

> 被评论的原文

评论正文
```

版式规则：

- **`---` + `# 评论（N 条）`** 作为边界，一眼能看出正文到哪里结束。
- **文末由我们追加的章节一律用一级标题（`#`）** —— 评论 / 附件 / 手写批注三处一致，正文自己的标题层级不受影响。
- **引用块（`>`）只用来引用被评论的原文** —— 这是 markdown 引用语法的本意。作者 / 时间走普通加粗行（`**作者** · YYYY-MM-DD HH:mm`），不再占用引用块。
- 时间固定成 `YYYY-MM-DD HH:mm`，**不用 `toLocaleString`**：导出产物不该跟着系统语言变。
- 同一串里的回复**平铺**输出，不缩进。

#### 两套评论存储完全不同

| | 协作笔记（锚定型） | 旧版笔记（评论区） |
| --- | --- | --- |
| 语义 | 选中一段文字再加评论 | 独立评论区，与正文无关 |
| 数据在哪 | 笔记自己的 doc JSON（`doc.comments`），**零请求** | 独立接口 `GET {kbServer}/ks/note/comments/{kbGuid}/{docGuid}?token=…`，每篇 1 次请求 |
| 定位方式 | `text[].attributes['comment-<id>con']` 行内锚点，也支持块级 `block.comments` | 无 |
| 被评论的原文 | `comment.abstract` | 没有，所以不产生引用块 |
| 回复 | `groupId === id` 是根，同组其余为回复 | `parentSN` 指向父评论 |
| 正文 | `blocks`（富文本） | `body`（纯文本 / 手写 markdown） |

`token` 与 `kbServer` 都来自 IndexedDB 的 `wiz-account/accounts` —— 协作笔记的 `doc.meta` 实测只有 `version / updatedBy / ctime / mtime`，既没有 token 也没有 apiServer。

两套存储是彻底分开的：拿协作笔记去调那个 comments 接口，`count` 返回 **0**（实测）。

#### 实现要点

- 应用自己的 `doc2markdown` 也支持 `keepComments`，但**我们没有用它**：它只吐“作者 时间 + 正文”，既不输出 `abstract`（被评论的原文），也不区分锚点，格式不受控。现在关掉它，由 `src/export/comments.ts` 自己拼章节。
- 评论正文复用应用自己的渲染器：`doc2markdown({ blocks: comment.blocks }, { keepComments: false })` —— 评论的 `blocks` 就是一份小 doc，转出来的规则和正文完全一致。
- 评论章节在 `rewriteImageTargets` **之前**拼进正文：评论里的图片要一起被改写并下载。（批注章节相反，必须在 `rewriteImageTargets` 之后拼，否则它注入的 `images/annotation-N.svg` 会被当成待下载资源。）
- 反转义（`unescapeMarkdown`）**只作用于笔记正文**，不作用于评论区：旧版评论的 `body` 是用户手写的 markdown，`\_` 可能是故意写的。
- 没有挂到任何锚点上的评论（孤儿）不导出 —— 应用自己也不渲染它们。

#### 只导出 HTML 的笔记类型：评论另落一个 `.md`

手写 / 公式这类笔记的正文只能导出成 HTML，**HTML 承载不了 markdown 章节**，所以勾了“包含评论”时，有评论就**额外产出一个同名 `.md`**：

```
<标题>.html      ← 正文
<标题>.md        ← 只有评论（第一行是 HTML 注释，说明正文在隔壁）
```

- 用 `path: ${baseName}.md` 塞进 `extractedFiles`，和 `.html` 成对、不会走散。
- **没评论就不落盘**，不会多出一个空文件。
- 两个文件 → 触发打包规则 → 单个笔记也会给 `.zip`（和 `.meta.json` 的降级是同一套规则）。
- 结果行会写明“评论 N 条（单独 .md）”，避免误以为评论在 HTML 里。
- 这类笔记不产生引用块（没有"被评论的原文"可引用）。

#### 其他

- 取评论失败（网络异常 / token 拿不到）时**不静默**：原因会写进结果行并计入“问题”页。

## 四、资源下载（图片与附件）

### 4.1 两种资源名，路径完全不同，不能互相转换

| 资源名形态 | 出现场合 | 访问路径 |
| --- | --- | --- |
| `index_files/xxx.png` | 老笔记 / Lite Markdown 笔记 / 渲染端上传的资源 | `/ks/note/view/{kbGuid}/{docGuid}/index_files/xxx.png` |
| 裸哈希 `xxxx.png` | 协作笔记自己的资源 | `/editor/{kbGuid}/{docGuid}/resources/xxxx` |

⚠️ 不要给裸名字硬补 `index_files/`：路径会走错，服务端会返回 **200 + 一张 1×1 占位图**。

`fetchResource()` 的校验顺序（每步的依据见 §4.1.1，**别调换**）：

1. **先挡占位图**（`looksLikePlaceholder()`）—— 本地服务 / 服务端对缺失资源返回的 1×1 GIF（实测 807 字节，content-type 还会跟着请求的扩展名撒谎）。不先挡掉，下一步的“按内容认格式”会把它当成真 GIF 收下；
2. **按内容认格式**（`sniffImageFormat()`）—— 字节确实是一种图片（PNG / JPEG / GIF / BMP / WebP / ICO / SVG）就收，**不看扩展名**；
3. 嗅不出格式时**退化**：只有“扩展名本来就没有魔数可校验”（如 `.tif` / `.heic`）且 content-type 看着像文件时，才按“长度 > 8”放行；其余一律判为“不是图片”并继续试下一个候选。

绝不把占位图、HTML 残页当成正文图片写进 zip。

另有一种情况：远程渲染出来的 HTML 里，图片可能已经是**可直接访问的地址**（协议相对 `//wiznote-desktop/...` 或根相对 `/...`）。这类引用直接请求，不要再当资源名拼路径 —— 判断“绝对地址”时只把 `http(s):` / `data:` / `blob:` / `file:` 视为外链保持原样，`//` 和 `/` 开头的仍然要下载。

> **结果里的“图片 成功/总数”**：`imageRefs` 是**本次要去 `images/` 落盘的文件数**，不是“引用次数”—— 同一张图被引用多次只会下载一次，报告里 `成功 + 失败 = 总数` 才自洽。（早先用的引用次数，会出现“图片 16/15 张”这种因为 HTML 侧图片没被计数而产生的怪值。）

#### 4.1.1 校验必须按**内容**，不能按扩展名（2026-10-07 实测）

同一批真实产物里，**扩展名与内容不符的真图**有一批，旧实现（按“扩展名对应的那一种魔数”查表）把它们全部判成“图片没取到”：

| 资源名 | 内容其实是 | 浏览器解码实测 |
| --- | --- | --- |
| `xxx.png` | JPEG（`FF D8 FF E0`） | 正常解码 ✓（多张、尺寸各异） |
| `xxx.jpg` | PNG（`89 50 4E 47`） | 正常解码 ✓ |
| `xxx.gif` | PNG | 正常解码 ✓ |
| `xxx.bmp` | WOFF 字体（`77 4F 46 46`，站点把它当 `@font-face` 用） | 非图片 |

所以**按内容认格式**、并且**落盘不改文件名**（图片解码本身就是按内容嗅探的，扩展名不影响显示）。

反面同样有实测：服务端对缺失资源返回的是 **1×1 的 `GIF89a`、正好 807 字节**，content-type 会跟着请求的扩展名变（`.png` 名字就声明 `image/png`）。旧规则“体积小 + GIF 头 + 扩展名不是 `.gif`”挡得住 `.png` / `.jpg` 名字，**挡不住 `.gif` 名字**（那种情况下扩展名与内容一致，魔数校验会放行 → 占位图会被当成真图写进产物；这就是 [site-internals.md §2.6](site-internals.md) 里原先只标着“仅推断、未实测”的那条风险）。现在按“**1×1 且正好 807 字节**”精确识别，与扩展名无关；非 `.gif` 名字仍保留旧的体积规则兜底。

还有一类“看着像图其实不是”，由第 2 步挡掉并**计入失败**（用户该知道）—— 服务端对缺失资源直接回**错误页**，实测四种：

| 返回 | 字节 | 是什么 |
| --- | --- | --- |
| `<title>Error_404_资源不存在</title>`（带 BOM） | 745 / 759 | 为知服务端的 404 页 |
| `<title>403 Forbidden</title>…nginx` | 146 | nginx 的 403 页 |
| `Bad Request`（HTML 4.01） | 324 | 服务端拒了这个请求 |
| 整份 HTML 页面（`<!Do…`） | 34 KB | 另一类兜底页 |

这类名字**真的救不回来**（在为知里打开那篇同样是破图）；能救回来的只有“服务端还有、只是本地缓存没填充”那种。

> 顺带记一笔：`.svg` 名字的宽松判断（“以 `<` 开头就当 SVG”）也在这轮收紧成 `<svg` / `<?xml` / `<!doctype svg`。实测有资源返回 324 字节的 `<!DOCTYPE…` 残页，旧判断会把它当假 svg 悄悄写进产物，现在如实报成失败。

#### 4.1.2 图片目标里的 title 要剥出来（2026-10-07 实测）

`rewriteImageTargets()`（`src/export/markdown-inline.ts`）处理的是宿主 `doc2markdown` 产出的 markdown，目标的形态比想象的杂：

| 形态 | 例子 | 处理 |
| --- | --- | --- |
| 普通目标 | `![x](index_files/a.png)` | 直接用 |
| 尺寸后缀（为知自己的约定） | `![x](index_files/a.png =300x200)` | 先剥 ` =…`，输出时原样补回 |
| 带引号的 title | `![x](index_files/a.png "截图")` | 剥出来，输出时补回 |
| 括号形式的 title（CommonMark） | `![x](index_files/a.png (标题))` | 剥出来，输出时原样补回 |
| **目标里带成对括号** | `![x](index_files/a(2).png)` | 按括号配对取，名字一个字符都不许少（见 §4.1.3） |
| **没加引号的 title** | `![x](images/a.png 截图)` | 剥出来并**补上引号**（这种写法按 CommonMark 根本不是图片引用） |
| 尖括号包住的目标 | `![x](<index_files/a b.png>)` | 取尖括号里的 |
| `\|` 分隔的多图 | `![x](a.png\|b.png)` | 逐段处理（为知的图集约定） |

没引号那种是实测踩到的：旧版 Markdown 笔记里原文是 `![截图](index_files/x.png&nbsp;"截图")`，经 `html2Doc → doc2markdown` 变成 `![截图](images/x.png 截图)`，旧实现把整串当资源名去请求（`index_files/x.png 截图`）→ 服务端查不到、返回 807 B 占位图 → 报“1 张图片没取到”，而那张图本身是好好的（几百 KB 的真图）。剥出来之后下载与渲染一起修好（产物里变成 `![截图](images/x.png "截图")`）。

判据见 `splitImageTitle()`：**第一个空格前带图片扩展名、后半不带** ⇒ 后半是 title。不能无条件按空格拆 —— `path sound` 这种本身就是带空格的文件名（实测存在）会被拆坏；`a(2).png` 这种**名字里自带括号**的也不能当 title（`(` 前面有空白才算）。

#### 4.1.3 目标里的成对括号不能截断（2026-10-07 实测，修过一次）

剪藏里“重名加 `(2)`”很常见，资源名会写成 `index_files/<hex>(2).png`。老写法用 `[^)]*` 取目标，会在**第一个** `)` 上截断：

| | 取到的名字 | 产物里那一处 |
| --- | --- | --- |
| 老写法 | `index_files/<hex>(2` | `![img](images/<hex>(2).png)` —— 链接目标其实是 `images/<hex>(2`，后面还挂着一截 `.png)` 残渣 |
| 现在 | `index_files/<hex>(2).png` | 与 zip 里的文件一致 |

两个后果都要命：① 拿一个不存在的名字去请求 —— 服务端回 807 B 占位图，**还会把它按那个错名字固化进本地缓存**（实测缓存里因此多出 `…(2).png` / `…(2` / `…(2.png` 三个变体，见 [site-internals.md §2.6](site-internals.md)），而真正存在的那张图就这么被报成“没取到”；② 产物被写坏（链接断 + 正文多出一截残渣）。

CommonMark 本来就允许裸目标里出现**配对**括号，所以现在按它的规则做括号配对扫描（`replaceInlineLinks()` + `findInlineDestEnd()`），不再用一条正则啃目标；附件链接那条（原来的 `LINK_SYNTAX`）同理，一并换掉了。解析全在 `src/export/markdown-inline.ts`，**刻意零依赖**，好让回归脚本直接 import，回归钉在 **`npm run check:markdown`**（33 项：`x(2).png`、嵌套括号、括号 title、`=尺寸`、`|` 多图、尖括号、外链、转义、跨空行，以及资源名在请求路径里的转义口径）。

### 4.2 协作笔记的图片必须直连真实源站

协作笔记的图片地址是 `${apiServer}/resources/${name}`，其中 `apiServer = https://{kbServer}/editor/{kb}/{doc}`。`kbServer` 跟账号走，需要运行时发现（§五）。

**不能**用虚拟主机 `//wiznote-desktop/...` 去取：Service Worker 处理 `/editor/**/resources/**` 时**按文件名查本地 OT 缓存、未命中就拿“请求自身的 host”去 `fetch`**（源码与逐步解释见 [site-internals.md §2.3](site-internals.md)）。

所以打 `//wiznote-desktop` 时那个 `fetch` 必然 DNS 失败（`TypeError: Failed to fetch`）。只有当编辑器**已经**把图片拉过一遍、缓存里有了文件名，虚拟主机才碰巧能用 —— 这正是“打开笔记后导出图片全失败、滚动一遍后全部成功”的真实原因。

`fetchResource()` 的候选顺序（实测对比，同一个 `xxx.png`）：

| 候选地址 | 结果 |
| --- | --- |
| `{kbServer}/editor/{kb}/{doc}/resources/xxx.png` | **200，真图（百 KB 级）** ← 可用 |
| `//wiznote-desktop/editor/{kb}/{doc}/resources/xxx.png` | `Failed to fetch`（缓存未命中时） |
| `//wiznote-desktop/ks/note/view/{kb}/{doc}/index_files/xxx.png` | 200，**807 B 占位图** ← 假图 |

**候选顺序按笔记类型分组**（`resourceUrls()`，2026-10-04 实测调过）：

```
协作笔记：  真实源站 / editor.buildResourceUrl
            → //wiznote-desktop/editor/…/resources/…（SW：先查本地 OT 缓存）
            → （跳过 /ks/…，它只会返回 807B 假图）

普通笔记等：//wiznote-desktop/ks/note/view/…/index_files/…（SW：本地数据服务，本地优先 + 联网兜底）
            → //wiznote-desktop/editor/…/resources/…
            → 真实源站 / editor.buildResourceUrl
```

> `doc.meta.apiServer` 这条路**不存在**：实测同步下来的 doc，`meta` 里只有 `version` / `updatedBy` / `ctime` / `mtime`，没有 `apiServer`。

**冷笔记实测（2026-10-07，用脚本自己的入口跑，不碰应用界面；本库批量数字见 `docs/private.local/samples.md`）**：对一批**从没打开过**的笔记（含协作笔记，靠 `syncOfflineDoc` 自己同步）批量取图，**几乎全部成功**；个别失败的那张**不是路径没走对** —— 把它的 6 条候选全试一遍（含没进候选表的 `{kbServer}/ks/…?token=`、括号编码两种写法），**每一条都只回 807 B 占位图**，`/editor/…` 那条 404 / `Failed to fetch`，即服务端确实没有这份字节。所以“用户得先在应用里渲染一遍”这个说法不成立（见 README 常见问题①）：能拿到的图，脚本自己第一步取 `index.html` 时就把它拉进本地了。

#### 为什么普通笔记必须把 `/ks/…` 放最前

**两条路都会被 Service Worker 接住并先查本地**，区别只在查的是哪个库 —— 所以“打网络地址”并不等于“真的走网络”，顺序决定的是**有没有先走对那条路**：

| 路径 | SW 先查哪个本地库 | 对另一类笔记的后果 |
| --- | --- | --- |
| `/editor/**/resources/**`（**含跨域真实源站**，SW 按路径路由、与 host 无关） | OT 资源缓存，按**文件名**查 | 对普通笔记**永远 miss** → SW 带 token 真去打源站 → **404，268 ms/张** |
| `/ks/**`（同源与 `//wiznote-desktop/` 一样） | 本地数据服务（笔记数据 + `wiz-note-resource`），按**裸名**查 | 命中即本地真图（3–5 ms）；miss 才联网兜底 |

- **协作笔记**：实测“真实源站 URL”由 SW 从本地 OT 缓存返回（20 ms，字节与 `wiz-ot-resource` 完全一致），所以放最前，一条都不浪费。
- **普通笔记**：`/editor/…` 是白跑（一篇 20 张图 ≈ 5 秒 + 服务端 20 条 404），它的资源只在 `/ks/…` 那条路的本地库里。
- 顺序调整**不改变“能不能离线导出”**：普通笔记的图本来就从 `/ks/…` 拿到，只是原先要先等两次失败。离线时两次失败也快，所以收益主要体现在在线时的延迟。

#### 资源名的编码必须跟浏览器一致

请求用的资源名就是笔记 HTML 里写的相对地址（形如 `index_files/icon@2x.png`）。口径只有一个：**浏览器解析相对地址时会怎么做** —— 本地缓存与本地数据服务都按**原始字符**认名字，多转义一个字符就等于换了个名字（缓存 miss → 服务端回 807 B 占位图，还把它按那个错名字固化进缓存）。同一个名字、两种编码的实测对照：

| 名字 | 原样请求 | 被 `encodeURIComponent` 过一遍 |
| --- | --- | --- |
| `index_files/icon@2x.png` | 200，**真图（KB 级 PNG）** | `…icon%402x.png` → **807 B 占位 GIF**（被魔数校验拒掉 → 记为失败） |
| `index_files/open[1].gif`（网页剪藏里的序号） | 200，**真图** | `…open%5B1%5D.gif` → 807 B 占位图 —— **整篇 17 张图全部报“没取到”，而应用里显示得好好的**（2026-10-08） |

所以 `encodePathSegment()` 用的是**白名单**（保留哪些字符），而不是给 `encodeURIComponent` 打补丁。保留集 = 字母数字 + `- . _ ~ ! $ & ' ( ) * + , ; = : @`（unreserved + sub-delims + `:` `@`）+ `[ ] ^ |`（URL 标准在路径里也不转义它们）+ `%`（HTML 里的引用可能**已经是** `%XX` 形式，浏览器解析相对地址时不会再转一次）；其余（空格、引号、`#`、`<` `>`、`?`、反引号、花括号、`/`、非 ASCII 与控制符）一律转义 —— `/` 要转是因为进到这里的是**单个路径段**（`index_files/` 前缀在外面）。

⚠️ 这一条**每漏一个字符就是一次“图片没取到”**（`@` 之后又漏了 `[` `]`），所以口径是“URL 标准里路径的 percent-encode set”，别再逐个字符打补丁；字符集那一组断言钉在 `npm run check:markdown`。

> 顺带一提：缓存里同一个资源可能出现两条（原始名是真图、编码名是 807 B 占位图），说明**用错的名字去请求，会把服务端返回的占位图按该名字固化进本地缓存**。

### 4.3 HTML 产物里的图片引用必须本地化

导出的 `.html`（只导出 HTML 的类型，以及“同时导出原始 HTML”的 sidecar）里，图片引用是 **应用渲染时写的原始地址**，不能原样保留：

| HTML 里的写法 | `file://` 下会解析成 | 结果 |
| --- | --- | --- |
| `index_files/x.svg`（相对） | 同目录 | ✅ 能显示（前提是文件真的在） |
| `/ks/note/view/…/index_files/x.svg` | 文件系统根 | ❌ 必然坏 |
| `//wiznote-desktop/…` | `file://wiznote-desktop/…` | ❌ 必然坏 |

所以导出时会把 `<img src>` / `<img srcset>` / CSS `url()` 里指向本地资源的引用统一改写成 `images/<文件名>`，并把资源记进下载清单（`localizeHtmlResources()`）。

- **和 markdown（以及附件）共用一个“资源名 → 文件名”分配器**（`createResourceNamer()`），所以同一张图在 `.md` 和 `.html` 里指向**同一个文件**，zip 里也不会存两份。分配器按“**子目录 + 文件名**”去重：`images/x.png` 与 `attachments/x.png` 互不冲突；附件用上传时的原始文件名，重名（或清洗非法字符后撞车）加 ` (2)` 后缀 —— 与 zip 里其他文件同一套规则，见 §1.4。
- CSS `url()` 只处理**图片扩展名**的地址 —— 那里的地址还可能指向字体 / 脚本，不该动。
- `http(s):` / `data:` / `blob:` / `file:` 视为外链，保持原样。
- **关掉“把图片下载到 images/”时不做任何改写** —— 和 markdown 侧一致，免得留下指向不存在文件的引用（此时 HTML 里的图片仍然是应用的原始地址）。
- 每个资源还会记下**被哪份产物引用**（`ResourceRef.referencedBy`）：markdown 正文先登记、HTML 后登记，语义是“**至少**出现在正文里”，所以两边都引用的图片记成 `markdown`。结果行据此分两句写 —— 正文缺图说“Markdown 里的图片会显示不出来”；只在 HTML（另附 HTML / 产物本身就是 HTML）里用到的站点皮肤、CSS 背景、字体缺了，说“Markdown 正文不受影响”，别让用户对着完好的 `.md` 找破图（见 §1.0 与 `session.ts` 的 `applyResultToRow()`）。

#### 外链样式表要内联进来

`<link rel="stylesheet" href="index_files/share.css">` 这类**本地**样式表也必须处理，否则：

- 控制台稳定报 `Failed to load resource: net::ERR_FILE_NOT_FOUND index_files/share.css`；
- 而且丢的往往是“保存的网页”这类笔记的**全部站点样式**（正文只剩内联的 `#wiz_custom_css`）。

做法（`inlineStylesheets()`）：按 `<link>` 的 `href` 取出资源名 → 取回文本 → 用 `<style data-wz-source="…">` 替换 `<link>`。几个关键点：

- **编码按 BOM 判断**，不能直接 `res.text()`：实测知乎的 `share.css` 是 `FF FE` + UTF-16LE，按 UTF-8 解出来是乱码，内联进去整篇样式都是废的（`fetchResourceText()`）。
- **CSS 里的相对 `url()` 以样式表自身所在目录为基准** —— `index_files/share.css` 里的 `url(bg.png)` 指的是 `index_files/bg.png`，先补目录再交给统一的分配器。
- 取不到就**把 `<link>` 删掉**（留着只会稳定报错），并记一条 problem 进“问题”页。
- 真·外链 CSS（`http(s):`）保持原样不动。
- **替换是“一趟做完”的**：先按 `matchAll` 的位置收集好所有 `<style>` 文本，再单遍重建字符串。别写成 `for (…) html = html.replace(tag, text)` —— 那是每个样式表都把整篇 HTML 扫一遍、复制一份（N 个样式表 = N 遍全篇，剪藏的几个 MB × 十几个样式表全在主线程上）。用**位置**而不是标签文本当 key 还顺带修掉旧写法的两个隐患：同一段 `<link>` 出现两次时只会改第一处、且 Map 会互相覆盖。

> 图片/样式表本身取不到时都**不静默**：图片计入“图片失败”，样式表写进 per-note 的 `problems`，两者都会出现在结果行的“问题”页里。

> **实测结论（2026-10-04）**：`file://` 下用**相对路径**引用同目录的图片是**允许**的（`<img src="pixel.svg">` 正常加载，`naturalWidth` 正确）；被拦的是 `fetch()` / XHR（`Failed to fetch`，因为 `file://` 是不透明源）。也就是说“HTML 只能内嵌图片才能看”是误解 —— 只要路径对、文件在，双击就能看。

### 4.4 附件（一）：协作笔记的 `embed` 块

笔记里**上传的文件**（PDF / Office 文档 / DrawIO 图…）在协作笔记的 doc JSON 里是 `type: 'embed'` 块，不需要额外接口：

```json
{
  "type": "embed",
  "embedType": "office",
  "embedData": {
    "src": "qj-….pdf",
    "fileName": "论文标题.pdf",
    "fileSize": 123456,
    "fileType": "application/pdf",
    "previewType": "card"
  }
}
```

按 `embedType` 分流（`collectAttachments()`，`note-content.ts`）：

| embedType | md 里的形态 | 处理 |
| --- | --- | --- |
| `image` | `![](资源名)` | 走图片那条路，落 `images/` |
| `office`（上传的文档 / 图片文件） | `[office](资源名)` | **附件**，落 `attachments/<原始文件名>` |
| `drawio` | `[drawio](资源名.svg)` | **附件**（它没有 `fileName`，退回资源名） |
| `webpage` | `[webpage](http(s)://…)` | 外链，不动 |
| `math` / `hr` / `toc` | 无资源可下（`math` 的 `src` 是 `data:`） | 不动 |

判定就一句：**`src` 存在、不是外部地址、且不是 `image`** → 当附件（`webpage` 的 `http(s):`、`math` 的 `data:` 天然被外部地址判断挡掉）。

两个容易踩的点：

1. **链接文案必须换掉。** 应用自己渲染出来的文案是 embedType（`office` / `drawio`），不是文件名 —— 原样保留的话，用户会得到一条写着“office”、指向 `attachments/qj-….pdf` 的链接。`rewriteAttachments()` 把它改写成 `[<原始文件名>](attachments/<原始文件名>)`，**只在文案正好等于 embedType（或文案为空）时才替换**，用户自己写的链接文案保持原样。
2. **zip 里的文件名与链接里的路径是两套写法。** 链接目标要做百分号编码（空格 / `#` / `(` 在 markdown 链接里会破坏语法或被当成 fragment），而 zip entry 用原始文件名；文件名本身还要过 `convertToValidFilename()` 清掉 `/`、`\` 等，防路径穿越。重名由分配器加 ` (2)` 后缀解决，所以同一篇里两个都叫 `1.pdf` 的附件会落成 `1.pdf` 与 `1 (2).pdf`（见 §1.4）。

下载走 `fetchAttachment()`（`app-bridge.ts`）：候选地址与图片**完全相同**，但**不能套图片那套校验** —— 附件的 content-type 是 `application/pdf` 之类，会被图片白名单（`image/*` + `application/octet-stream`）直接判死；扩展名也没有内容特征，`sniffImageFormat()` 对它们只会返回空，反而会放行 807 B 占位图。所以改成**反过来识别占位图**（`looksLikePlaceholder()`，规则见 §4.1.1）。

> **实测（2026-10-04，xapp 0.1.107）**：`{kbServer}/editor/{kb}/{doc}/resources/{名}` 返回 200 + `application/pdf`、文件头 `%PDF-1.7`（不带 `?token=` 也能通 —— Service Worker 会自己补 token）；`//wiznote-desktop/…` 在缓存未命中时 `Failed to fetch`。真实导出产物核对：该附件按原始文件名落在 `attachments/` 里，md 里的链接文案与路径一致，结果区显示“附件 1/1 个”。

> **普通笔记的附件是另一套机制**（`attachments` 表 + `/ks/attachment/download`），见 §4.5。

### 4.5 附件（二）：普通笔记的 `attachments` 表

普通笔记（含旧版 Markdown / 保存的网页 / `document`）的附件跟协作笔记毫无关系：**清单优先读本地 `attachments` 表（零请求），不够用时联网补一次；下载走 `/ks/attachment/download/`；正文里只有“引用”，没有清单**。

| 环节 | 依据 | 说明 |
| --- | --- | --- |
| 有哪些附件 | ① 本地 IndexedDB `wiz-<库>.attachments`（主键 `[kbGuid+docGuid+attGuid]`）② 服务端 `GET {kbServer}/ks/note/attachments/{kb}/{doc}?token=…` | 只有它们带**原始文件名**。① 整表读一次建索引后缓存（批量导出不做平方级扫描）；只有当 ① 看着不完整（没有这篇的行 / 行数少于 `attachmentCount` / 有行的名字缺失只剩 guid）时才用 ② 补一次 |
| 正文哪里引用了 | 原始 HTML 里的 `<a href="wiz://open_attachment?guid=…">` | 实测写法是 `<a href="wiz://open_attachment?guid=X"><img src="index_files/X_image.png" class="wiz-img-attachment"></a>` |
| 下载 | `GET {kbServer}/ks/attachment/download/{kbGuid}/{docGuid}/{attGuid}` | 见下 |

**三个实测出来的坑（2026-10-04，xapp 0.1.107）**：

1. **`html2Doc → doc2markdown` 会把整个 `<a wiz://…>` 丢掉**，只留下里面那张预览图 `![](index_files/{attGuid}_image.png)`。所以不做处理的话，导出的是**服务端重新编码过的预览图**，原始文件和文件名全丢 —— 实测预览图经过重编码，甚至可能比原始文件还大。
2. **附件可能完全不出现在正文里**。老式“附件面板”式笔记（实测有一篇挂多个附件、正文却零引用：HTML 里 `wiz://` 0 处、`<img>` 0 个、`index_files` 0 处）只能靠清单发现，位置信息不存在。
3. **本地表里可能根本没有这篇笔记的行**（附件元数据没同步下来）。这**不是限制**：清单能联网从 `/ks/note/attachments/…` 拿回来（应用自己的附件面板用的就是这个接口，它才是权威来源，本地表只是缓存）。只有联网也拿不到（离线 / 关掉“允许联网补全”/ 没有 token）时才会少导出。

对应处理（`planNoteAttachments()` / `rewriteNoteAttachments()`，都在 `note-content.ts`）：

| 情况 | 处理 |
| --- | --- |
| 正文引用了附件 | 把那句 `![…](index_files/{attGuid}_image.png)` **整句换成** `[<原始文件名>](attachments/<原始文件名>)` |
| 清单里有、正文没引用 | 文末追加 `# 附件（N 个）` 章节，逐条列出链接 |
| 本地表缺行 / 行数不足 | 先联网补清单（一次 `/ks/note/attachments/…`）；清单也拿不到时，正文引用到的再按 attGuid 问一次 `/ks/attachment/info/…` 要名字，正文没引用的则写进“问题”页 |

几个必须守住的地方：

- 替换要在 `rewriteImageTargets()` **之前**做。否则那张预览图会被当成正文图片下载进 `images/` —— 于是产物里同时有“预览图”和“原始附件”两份，还都不是同一张图。
- 文末章节要**兜住所有没落地的附件**：正文引用了、但那张预览图没出现在 markdown 里的（`html2Doc` 可能吃掉），也要列进去；否则文件进了 zip 却没有任何地方引用，用户根本找不到。
- 名字要按“本地表 → 清单接口 → attGuid”三级兜底，否则落盘的是一串 attGuid **连扩展名都没有**（`.png` 那种信息在文件名里）。前两级都要 token。
- **清单合并而不是覆盖**：服务端清单理论上更权威，但万一它被分页/截断，**覆盖会静默丢附件**；合并最坏只是多试一个已失效的 guid（下载 404，会被算进“附件失败”并报出来）。所以 `listNoteAttachments()` 按 attGuid 取并集、服务端的名字优先。
- **少导出不能是静默的**：笔记对象上有 `attachmentCount`（应用同步下来的快照），拿它和实际计划导出的数量比一下，少了就往 `problems` 里写一条 —— 否则用户只看到“附件 0 个”，完全不知道笔记里其实挂着 6 个附件。⚠️ 它只是**提醒**而非断言：服务端删过附件的话这个数不会跟着变小，所以只在“少了”时才提示。
- 链接编码与协作笔记那条路统一走 `encodeAttachmentName()`。实测踩过：只写 `encodeURIComponent` 时，文件名里的 `'` 不会被编码（而 `&` 会），于是两条例子的编码规则不一致。
- 取数通道不同，`ResourceRef` 上用 `channel` 区分：协作笔记的 `office` 附件是 `resource`（按资源名走 `/resources/`），普通笔记的附件是 `attachment`（按 attGuid 走 `/ks/attachment/download/`）。

**下载接口的实测细节**：

- **必须带 token**：带 token → 200 + 原始字节（文件头 `89 50 4E 47`）；**不带 token → HTTP 500**（`text/plain`，21 字节）。所以代码**先带 token 试**，失败再退回不带 token（provider 版本不同时有兜底）。
- ⚠️ **别只按 HTTP 状态码判断成功**：同一个 token 校验在三个接口上的表现并不一致 —— 下载接口缺 token 是 **HTTP 500**，而 `/ks/attachment/info/…`、`/ks/note/attachments/…` 缺 token 是 **HTTP 200 + `returnCode: 301 Invalid token`**。这个坑真踩过（只看状态码会得出“不需要 token”的错误结论）。完整对比见 [site-internals.md §2.7](site-internals.md)。
- **虚拟域 `//wiznote-desktop` 走不通**：SW 的本地数据服务只实现了 `/ks/note/view/**` 一类路由，这条路径不在其中，miss 之后 SW 拿请求自身的 host 去拉 → DNS 失败（实测 `Failed to fetch`）。所以必须打真实 `{kbServer}`。
- attGuid 不存在时返回 **404**（`Not Found`），不会返回假数据；占位图那道还是照旧留着（`looksLikePlaceholder()`）。

> **`dataSize` 不可信**：本地行里是 `0`，服务端 list 接口也返回 `0`，而真实文件是有字节的。别拿它做校验或提前显示大小 —— 实测导出后的真实字节数与表里的值对不上。

> **验证（2026-10-04）**：一篇正文引用型（PNG 附件）→ 结果区 `附件 1/1 个`，zip 里落的是**原始文件**（不是那张重编码过的预览图），md 里那句预览图被换成了附件链接，`images/` 里不再有它；另一篇挂了 6 个图片附件、正文零引用 → `附件 6/6 个`，6 个文件按原始文件名落进 `attachments/`，md 文末多出 `# 附件（6 个）` 章节。
>
> **降级路径也实测过**（把本地 `attachments` 表整表清空、跑完再原样恢复）：① 那篇多附件的笔记仍是 `附件 6/6 个`、`问题 0`，文件全按原始文件名落盘 —— 靠的是**一次 `/ks/note/attachments/…` 清单请求**（网络日志：清单 1 次、下载 6 次）；② 正文引用型那篇仍是 `附件 1/1 个`，而且 `info` 请求数为 **0**（清单接口已经把名字带回来了，`/ks/attachment/info/…` 只是更后一层的兜底）；③ 只有**联网也拿不到清单**时才会少导出，那时“问题”页写明“有 N 个附件，但没能拿到它们的清单（本地没有、联网也没取到），一个都没导出”——**不再静默**。
>
> 常规路径（本地表完整）额外网络请求数为 **0**：实测导出那篇多附件的笔记，清单 / 详情请求都是 0 次，只有下载若干次。

### 4.6 附件（三）：只导 HTML 的那几类笔记

手写 / 旧版 `.mj` 公式笔记的产物是**原始 HTML**（见 §3.2），附件走**同一套清单、命名与计数**（`planNoteAttachments()`），对 HTML 只做**一处最小改动**：

> **把正文里已经存在的附件链接指向 `attachments/<文件名>`，绝不新增原文没有的段落。**

| 情况 | 处理 |
| --- | --- |
| 正文引用了附件 | `<a href="wiz://open_attachment?guid=…">` 的 href 换成 `attachments/<原始文件名>`（只动这一个属性，class / style 等其余部分原样）；里层那张预览图不动，仍由 `localizeHtmlResources()` 收进 `images/`，所以页面观感与编辑器里一致，只是"点击"从宿主打开变成打开本地文件 |
| 清单里有、正文没引用 | **只落进 `attachments/`，不在页面里露面** —— 不注入“附件”章节、也不产生任何新节点 |

为什么必须改 href：`wiz://` 是宿主（桌面端壳）自己的协议，导出的静态文件里点不开；而且那个地址只带附件 guid、没有 kb/doc 上下文，脱离宿主也定位不到附件。

> 这条规则对**产物里的所有 HTML** 都生效：只导 HTML 的那几类，以及“同时导出原始 HTML”的 sidecar（§3.1）—— 两者的附件链接都会被改写成 `attachments/<文件名>`。sidecar 实测：改写后 `wiz://open_attachment` **0** 处、`href="attachments/"` **1** 处。

为什么**不**注入章节：HTML 产物的定位是**保真备份**（手写 / 公式转 markdown 会丢东西，所以给原样 HTML），凭空多出一段原文没有的“附件”列表属于篡改页面结构。markdown 那条路没有"页面"可言，才需要把正文里那张预览图换成链接（§4.5）。

结果区照旧显示 `附件 N/M 个`（`attachmentRefs` 来自资源清单，与 markdown 路共用）；清单两边都拿不到时同样走 `attachmentProblemList()` 提示。

**实测（2026-10-04）**：

- 一篇正文引用型（PNG 附件）→ `成功 1 篇 · 图片 2/2 张 · 附件 1/1 个`；改写后的锚点是 `<a href="attachments/<编码后的文件名>"><img src="images/{attGuid}_image.png" class="wiz-img-attachment" …></a>` —— 原文里 `wiz://open_attachment` 出现 **0** 次、`href="attachments/"` **1** 次、无注入章节；zip 里同时有附件本体（`attachments/`）与预览图（`images/`）。
- 一篇挂 6 个附件、正文零引用 → `附件 6/6 个`，6 个文件按原始文件名落进 `attachments/`，HTML 里 `href="attachments/"` **0** 次、无注入章节。

> ⚠️ 上两条是**临时改一行类型判定**（让普通笔记也走 HTML 兜底）测的 —— 暂无“手写 / 公式 + 带附件”的真实样本（手写与公式这两类都没有可用样本）。改动已撤销（`grep -rn TEMP-VERIFY src/` 为空）。

> 顺带一提：这类 HTML **只带附件链接**，不会有附件清单 —— 正文没引用的附件要自己去 zip 的 `attachments/` 里翻。这是“只改链接、不插段落”的必然代价。

## 五、协作笔记的联网补全

协作笔记的**正文只存在 OT 服务器上**，唯一获取途径是开一条只读 WebSocket（`LiveEditor.syncOfflineDoc`）。前提是知道知识库服务器地址 `kbServer`。

### 5.1 怎么拿到 `kbServer`

它在**应用的 IndexedDB 里**，页面同源可直读，零请求零猜测。实测（2026-10-03，xapp 0.1.107）：

| 来源 | 内容 |
| --- | --- |
| `wiz-account` → `accounts` | `{ kbGuid, kbServer: 'https://vipkshttpsN.wiz.cn', serverUrl: 'https://as.wiz.cn', token, ... }` |
| `wiz-<guid>` → `kbs` | 每条知识库记录也带 `kbServer`（商务/共享库走这里） |

`fetchKbServer()` 先查 `wiz-account`（按 `kbGuid` 精确匹配），再扫各知识库库的 `kbs`，结果按知识库缓存。

> ⚠️ **别走 `/as/**` 接口。** 它**不**被 Service Worker 代理，`//wiznote-desktop/as/user/groups` 会直接 `ERR_NAME_NOT_RESOLVED`。
>
> ⚠️ **也别拿 `location.origin` 去猜。** `syncOfflineDoc` 先发一次 HTTP 握手 `GET {origin}/editor/{kb}/{doc}/auth`；猜错就是 404 + `http auth error`，白等一轮超时。
>
> 这两个坑都真踩过，所以现在的实现只认 IndexedDB。

### 5.2 两条路径

1. **`LiveEditor.syncOfflineDoc(kbServer, kb, doc)`** —— 开只读 WebSocket 同步整篇。实测：`syncResult: true`，`getOfflineDocData` 随即能读到完整 block，图片也随之进入 SW 缓存。
2. **触发 Service Worker 下载** —— 请求 `/ks/note/view/…/index.html` 时，SW 的拦截器第一步会跑 `getDoc(kb, doc)`。

第 2 条只作兜底：实测对协作笔记它**只下载元数据**，正文仍然读不到（`gotHtml: true` 但 `getOfflineDocData` 依然为空）。

全部失败时**明确跳过并提示“请先在应用里打开它一次”**，不会产出假文件。

⚠️ 另有一种“假失败”：**SW 没接管页面**时，所有 `//wiznote-desktop/**` 请求都会 `Failed to fetch`，症状与“笔记不在本地”完全一样（连本地**已缓存**的笔记也会失败）。这时提示后**多带一句“本地离线服务没接管页面，刷新一次再试”**（`isLocalDataServiceReady()`，原理见 [site-internals.md §2.5](site-internals.md#25-调试注意)），否则用户会以为笔记没同步。

### 5.3 ⚠️ 协作笔记不能用 `index.html` 当正文

那个接口是旧版笔记的渲染通道，对协作笔记只会返回“当前客户端版本较低，无法编辑协作笔记”的**占位页**。`html2Doc` 会把占位页忠实地转成一份“看起来很正常”的文档，产出一份几百字节的假 `.md` —— 曾经真的踩过这个坑（导出的“笔记”只有几百字节）。

### 5.4 宿主解析不出来时，不能整篇丢

实测（2026-10-07，xapp 0.1.107）：正文里只要有**没有单元格的 `<table>`**，宿主的 `html2Doc` 就会返回 `undefined`（`<table></table>`、`<table><tbody></tbody></table>`、`<table><tbody><tr></tr></tbody></table>` 三种都复现，带 `<td>` 的正常），原来那句 `if (!doc) return { ok: false, detail: '无法解析笔记内容' }` 于是把整篇（哪怕正文与图片都在、体量不小）判成“跳过”，用户看到的就是“已跳过 · 无法解析笔记内容”，连勾了“同时导出原始 HTML”也没有任何产物。

现在的处理是三段式，**每一段都不能省**：

1. **重试**：第一次失败且 HTML 里有 `<table>` 时，用 `stripCellLessTables()` 摘掉那些没有单元格的表再解析一次（空表按定义没有内容，摘掉无损；实测那篇保存网页摘掉空表后即可正常产出 markdown）。只在这一步失败后才付“重新序列化整篇 HTML”的代价，正常笔记一次都不走；
2. **HTML 兜底**：仍然失败、且用户勾了“同时导出原始 HTML”时，把**已经拿到手的原文**按 HTML 产物落盘（`buildHtmlOnlyResult()`，与手写 / 公式那几类共用），并在“问题”页写明“应用的 HTML 解析器处理不了这篇的正文，没能转成 Markdown，已改为只导出原始 HTML”；
3. **跳过**（没勾那个选项时）：原因必须**可操作** —— “勾选『同时导出原始 HTML』可以至少保住原文”，而不是一句无法区分的“无法解析笔记内容”。

> 判定依据：解析失败与“笔记本来就是空的”是两回事，前者有原文可救、后者没有；提示文案必须能把它们分开。

`fetchNoteHtml()` 里加了一层占位页识别（`isUnsupportedPlaceholder`），命中就判为无内容，绝不产出假文档。

## 六、富文本笔记里的“markdown 字面文本”要先反转义

很多从 markdown 导入的笔记类型其实是 `document`（富文本），结构是这样：

```html
示意图：<br /><br />![](index_files/pic.jpg)<br /><br />
...
<ed_tag name="markdownimage" style="display:none;">
  <img src="index_files/pic.jpg">
</ed_tag>
```

正文里的 `![](…)`、`[TOC]`、`**粗**`、`$\mu$` 都是**字面文本**，`doc2markdown` 会把它们转义成 `!\[\](index\_files/x.png)`，好让编辑器按字面显示。

于是导出会踩两个坑：

1. `.md` 里是 `!\[\](...)` —— 在 markdown 里这就是一行普通文字，**图片、目录、粗体、公式全部失效**；
2. `rewriteImageTargets` 匹配不到带反斜杠的写法 → `imageRefs = 0` → **不打包，只出一个 md**。

所以 `html2Doc → doc2markdown` 这条路上加了 `unescapeMarkdown()`。实测（同一篇笔记）：

| | 反转义前 | 反转义后 |
| --- | --- | --- |
| 正文 | `!\[\](index\_files/x.png)` | `![](index_files/x.jpg)` |
| 图片引用数 | 0 | 与正文里的引用数一致 |
| 下载 | 不打包 | 打包，且都是真图 |

只在这条路上反转义：**Lite Markdown 笔记的正文是用户手写的 markdown，`\_` 可能是故意写的，不能动。**

**额外收益：URL 也一起修好了。** `doc2markdown` 会转义正文里 URL 的下划线（如 `?x=1&mo\_device=1`）。这个转义在 markdown 链接目标里虽然合法，但 URL 一旦被复制出去就是坏的。`unescapeMarkdown()` 同样处理了它，实测正文里的转义 URL 全部还原成 `mo_device`。

### 6.1 只还原宿主真正会转义的字符

`unescapeMarkdown()` 的字符集**不是**照抄 CommonMark 的“可转义标点”全集，而是**精确对齐宿主的转义行为**：实测（2026-10-09，xapp 0.1.107）`LiveEditor.escapeMarkdownText()` —— 宿主自己给正文转义用的那个函数 —— 只转义 6 个字符：

| 字符 | 宿主输出 | 我们是否还原 |
| --- | --- | --- |
| `[` `]` `_` `*` | `\[` `\]` `\_` `\*` | 还原（图片 / 目录 / 粗体靠它才生效） |
| `$` | `\$` | 不还原（见下） |
| `\` | `\\` | 不还原（见下） |

于是正则收窄成 `/\\([\[\]_*])/g`（`markdown-inline.ts` 的 `unescapeMarkdown()`，**刻意零依赖**，回归用例在 `npm run check:markdown`）。

**这是实测纠正过来的 bug（2026-10-09）。** 早先的实现把集合写成了 CommonMark 的标点全集（反引号、花括号、圆括号、`#` `+` `-` `.` `!` `>` `~` `|` 都在内），这些字符宿主**根本不会转义**，多还原一个就是把公式里的 LaTeX 转义改坏 —— `\|`（范数）、`\{` `\}`（字面花括号）、`\(` `\)`（行内公式定界）都是**原文**，被还原后公式就坏了。

两个**刻意不还原**的字符，各是一处取舍：

- **反斜杠**：公式里的 `\\` 是 LaTeX 换行符（`doc2markdown` 对公式内容是**原样输出**，不转义），而正文里字面的 `\` 会被转义成 `\\`。两者在字符串上长得一模一样、无法区分；公式里的 `\\` 远比正文里的字面反斜杠常见，所以保留 `\\` 不动 —— 正文里的字面反斜杠留在产物里是 `\\`，markdown 渲染出来仍是单个 `\`，**观感一致**。
- **`$`**：正文里字面的 `$` 会被转义成 `\$`。不还原同样是刻意的 —— `\$` 渲染出来就是 `$`，还原反而可能让“成本 $100，而公式是 $x$”里的两个 `$` 被渲染器配成一段公式。

**症状与归因（2026-10-09）**：在宿主里选中正文右键“剪贴板 → 复制为 Markdown”，拿到的是正确的 `\\`；而我们的产物是 `\` —— 差别就在这一层反转义：宿主的复制功能**不做**反转义，我们做了、且做过头了。

## 七、手写批注层（覆盖式）的处理

为知笔记有两种“手写”相关的东西，**形态完全不同**：

| | 插入手写 | 文章标注 |
| --- | --- | --- |
| HTML 形态 | `<img class="wiz-svg-image" src="index_files/xxx.svg">` | `<wiz_marker id="wiz-painter-root">` + 内联 `<svg class="wiz-svg-base">` |
| 语义 | **内容块**，在正常文档流里 | **覆盖层**，`position:absolute; z-index:1000` 贴在版面上 |
| 坐标 | 自带像素尺寸 | 相对笔记版面（viewBox 与正文宽度一致） |
| 导出 | 当普通图片处理，天然正确 | 见下 |

`html2Doc` 不认 `wiz_marker`（不是内容模型里的块类型），会**整层丢掉** —— 不处理的话，用户会拿到一份没有任何批注痕迹、却看起来“导出成功”的 md。实测（2026-10-03）原始导出结果只剩几十字节：

```
![image](images/svgFile_<时间戳>_<序号>.svg)

文本
```

### 7.1 处理方式：降级保留 + 明确提示

1. **提取** —— 从 HTML 里捞出每个 `<wiz_marker>` 内的 `<svg class="wiz-svg-base">`（`extractAnnotations()`）；
2. **降级保留** —— 存成 `images/annotation-N.svg`（与真实图片共用同一个分配器：图片先占位，同名时批注图层让位成 `annotation-N (2).svg`，见 §1.4），在 md 末尾追加批注章节，并说明“原本叠在正文版面上”；
3. **提示** —— 结果区显示“手写批注 N 层”与原因。

整理成独立 SVG 时有三个必须处理的地方：

| 问题 | 原因 |
| --- | --- |
| `viewbox` → `viewBox` | HTML 属性名不区分大小写，独立 `.svg` 是 XML、**区分大小写**，不改就解析不出尺寸 |
| 去掉 `class` / `id` | 原本依赖页面样式，独立成文件后没意义，`id` 还可能撞 |
| 补白底 `<rect>` | 原本是叠在白纸上的透明层，独立成文件后加白底，深色主题下也能看清 |

> **为什么不做“完整还原”**：批注是**版面依赖**的。markdown 是纯文本流，宽度 / 字号 / 分页都会变，笔画坐标必然对不上原文。硬贴回正文只会误导读者，所以只做“不丢数据 + 说清楚”。

> **关闭“下载图片”时**：不追加批注章节（避免留下指向不存在文件的引用），但**计数照旧上报**，结果区依然会提示这篇有批注没导出来。

### 7.2 导 HTML 时不需要处理

手写 / 旧版公式笔记走 HTML 兜底，批注层本来就在 HTML 里（`<wiz_marker>` + 内联 SVG），而且其样式在 `<style id="wiz-marker-style">`（**不带** `unsave` 标记，不会被 `sanitizeNoteHtml()` 剥掉），打开就能正常渲染。

### 7.3 协作笔记：不适用

**协作笔记本身就不支持批注功能**，所以不存在漏检 —— 它走 doc JSON 这条路径不会漏掉任何东西，无需额外处理。（已确认，不是限制。）

## 八、笔记元数据

**默认开启**。按笔记形态分三种落盘情况：

| 笔记 | 形态 | 产物 |
| --- | --- | --- |
| markdown + YAML 模式 | 写进正文开头的 front matter | 1 个 md |
| markdown + JSON 模式 | 同名 `.meta.json` | md + meta.json |
| HTML（手写 / 公式） | **一律 json**（装不下 YAML，见 §8.4） | html + meta.json |

### 8.1 数据从哪来：零网络

**几乎全部来自已经在手的笔记对象**（导出时从 React fiber 上取到的那一个），不需要查 IndexedDB、不需要任何网络请求。实测（2026-10-03）该对象上有 34 个元数据字段。

两个例外，都只读 IndexedDB，**仍然零网络**：

**① 标签要查主库的 `tags` 表**：`note.tags` 是 `guid1*guid2` 形式的 guid 列表，不是名字。关键点是**这张表是树** —— 每一行都带 `parentGuid`，应用自己按 `children` 渲染成缩进树（bundle 里 `hasSameChildTag(parentGuid, name)`，同名只约束在同一父下），所以我们把它拍平成**完整路径**：

| 规则 | 说明 |
| --- | --- |
| 分隔符 `/` | 应用**没有自己的路径字符串约定**（UI 是缩进树），`/` 是 front matter 生态里嵌套标签的通行写法（Obsidian `#父/子`、Dataview 可按层级筛） |
| 顶层标签的父是字面量 **`rootTagGuid`** | 不是 guid，`tags` 表里也没有这一行；走到它就停 |
| 父查不到 → 停 | 本地可能只同步了子树；停，只保留已收集的段，**不臆造**父名 |
| 环保护 + 段数上限 | 纯防御：自环 / 互指 / 超长链不该让导出卡死 |
| guid 解析不到 → 原样保留 | 不静默丢（沿用旧行为） |

为什么要拍路径而不是只取 `name`：**跨父同名**的标签只有路径能区分，而多级标签在实际数据里很常见（占比与层级分布见 `docs/private.local/library-stats.md`）。实现是纯函数 `buildTagPaths()`（`src/export/tag-path.ts`），脏数据（自环、互指、缺父、超长链、跨父同名）全部在 `npm run check:frontmatter` 里覆盖。

**② `note.tags` 为空时回落到本地 `docs` 行**（`readNoteTags()`）。实测（2026-10-04）：从**列表**右键导出时，我们拿到的是列表接口给的 DTO，它上面的 `tags` 是**空串**，而同一篇的 `docs` 行里明明有标签 —— 只信笔记对象会让标签**静默消失**（front matter 里连 `tags` 键都不出现）。这是实测发现并修掉的坑。

### 8.2 字段清单

**顶层友好字段**（空值不写）：

`title` / `created` / `modified`（对应笔记对象的 `dataModified`）/ `accessed` / `category` / `tags` / `url`

**`wiznote` 块**（默认关闭，勾选“附带 WizNote 原始字段”后才有，定位是排查用）：`docGuid` / `type`（原始值）/ `fileType` / `version` / `readCount` / `infoModified` / `status`

刻意**不导出**的字段：

| 字段 | 原因 |
| --- | --- |
| `dataSize` | **实测值恒定、且与真实大小无关，完全不可靠** |
| `markers` / `styleGuid` | 实测全空 / 全 null |
| `protected` | 实测全 0 |
| `author` | 实测全空 |
| `iconIndex` / `coverImage` / `abstractImage` | 纯 UI 索引，脱离应用没意义 |
| `params` | 绝大多数是空对象；有值的几乎全是 0 且语义不明 |
| `seo` | 分享标识，三种形态混用，像历史遗留 |
| `dataMd5` / `infoMd5` / `paramMd5` | 校验值，不做同步对比就没用 |

> `status` 是**同步状态**（`serverDataModified` / `normal`），不是删除标记。它偏临时，所以只放进默认关闭的原始块里，不写进常规导出结果。

### 8.3 三个必须处理的坑

1. **字符串 `'null'`** —— 有些字段真的存了字符串 `'null'`（实测 `keywords` 出现过），`clean()` 一律当空，否则会写出 `keywords: "null"`；
2. **YAML 引号与转义** —— 标题 / 标签里的 `:`、`#`、`|`、引号、换行都会破坏结构。这件事**已交给 js-yaml**，不再手写（为什么、以及手写版踩的两个坑见 §8.5）；
3. **数字字段不能加引号** —— `version` / `readCount` 本来就是数字，加引号会变成字符串、没法比较大小，所以由 `NUMERIC_FIELDS` 单独处理。（这条是第一版实测输出里发现的：把数字 `version` 写成了带引号的字符串。）

时间统一用 **ISO 8601 带本地时区偏移**（`2024-01-02T03:04:05+08:00`）而非 UTC：对用户来说时间是“本地几点”，转 UTC 要心算；同时它仍可解析、可直接排序。

### 8.4 HTML 为什么只能 json

YAML front matter 是 markdown 的专有约定，HTML 没地方放。硬塞只能改成注释块或 `<meta>` 标签，那是另一套字段命名。所以统一降级成 json，保持 **一套字段结构、两种容器**。

代价：单篇 HTML 笔记 + 元数据 → 2 个文件 → 必然打包 zip（结果区会说明）。

### 8.5 YAML 序列化：交给 js-yaml（以及为什么不再手写）

第一版是自己判“哪些字符串必须加引号”（特殊字符集 + 布尔 / null 形状 + 数字形状 + 日期形状）。拿真实解析器（pyyaml 6.0.3 = **YAML 1.1**，比多数消费者更严格）和一批极端值逐条对拍，那份启发式挂了 8/54：

| 输入 | 手写产物 | 后果 |
| --- | --- | --- |
| `- dash` | `title: - dash` / `tags: [- dash]` | **YAML 语法错误**（`sequence entries are not allowed here`） |
| `vt\x0bhere`、`nul\x00here`、`bel\x07here` | 原样写进文件 | **解析器拒收**（`unacceptable character #x000b`）→ 整份 front matter 读不出来 |
| 孤立 `\r`、NEL(`\u0085`) | 引号包住了，但转义只认 `\r?\n` | 被 YAML 当换行**折叠成空格**，值变了 |

这类“看着无害的字符”清单列不完，所以换成成熟库：`js-yaml` 的 `dump()`，**同一批值 0 失败**。它的 dumper 偏保守：`yes` / `on` / `2024-01-01` 这类**字符串**会主动加引号（YAML 1.1 里它们是布尔 / 日期），NEL / LS / PS 写成 `\N` / `\L` / `\P`，控制字符写成 `\x..` / `\u....`。`renderFrontMatter()` 现在就是“拼一个普通对象 → `dump()`”。

三个参数必须显式设，否则产物会悄悄变样：

| 选项 | 不设会怎样 |
| --- | --- |
| `lineWidth: -1` | 默认 80 列会**折行**，长标题 / 长 URL 被折成多行 |
| `quoteStyle: 'double'` | 默认单引号（`'2024-01-02T…'`），与第一版产物的双引号风格不一致 |
| `noRefs: true` | 默认可能写锚点 / 别名（`&ref_0` / `*ref_0`），正常数据用不到，出现只会更难读 |

⚠️ **我们用的是 js-yaml 5**（重写过的版本，API 与 4.x 不同）：引号风格是 `quoteStyle: 'single' | 'double'`，**不再是** 4.x 的 `quotingType: "'" | '"'`（照抄 4.x 写法会被 `tsc` 拦下）。它**自带 `DumpOptions` 类型**，所以不需要 `@types/js-yaml`。同时它是本项目第二个运行时依赖（第一个是 `fflate`）：实测只引 `dump` 时 **31.9 KB min / 9.9 KB gzip**（`argparse` 只在它自己的 CLI 里用，tree-shake 后没进产物）。

一个可见的排版变化：**标签数组现在是块状**（每行一个），不再是行内 `[a, b]` —— js-yaml 没有“只让某个集合走 flow”的开关，而块状本来也是 front matter 里更常见的写法。

> **回归检查**：`npm run check:frontmatter`（`scripts/check-front-matter.mjs`，不依赖测试框架，Node 直接跑 TS）。把上面那批极端值 + 若干结构断言（裸控制字符、锚点 / 别名、不折行、字段顺序、数字仍是数字、同名标签）以及**标签层级拍路径**的脏数据（自环、互指、缺父、超长链、跨父同名、空标签）钉住，共 **75 项**。判定器是 js-yaml 自己，属“自产自检”，所以额外加了**不依赖解析器**的结构断言；当初那批更强的判定器是 pyyaml（YAML 1.1）。

实际产物长这样：

```yaml
---
title: 示例笔记
created: "2024-01-02T03:04:05+08:00"
modified: "2024-01-02T03:04:05+08:00"
accessed: "2024-01-02T03:04:05+08:00"
category: /示例分类/子分类
tags:
  - 示例标签
  - 子标签
  - "- 手写"
url: https://example.com/x?y=1
wiznote:
  docGuid: abc-123
  type: document
  version: 13875
---
```

（`version` 是数字不加引号；时间被引号保成字符串，不会被 1.1 解析器读成日期对象。）

## 九、Markdown 转换本身

能转 Markdown 的类型全部收口到应用自己的 `LiveEditor.doc2markdown`，所以公式（`$$…$$`）、图片、mermaid / plantuml / flowchart、代码块、表格、列表的处理规则和应用自身完全一致。

各类型走哪条路（Lite 走原文、协作走 doc JSON、其余走 HTML → doc）见 [note-types.md § 三](note-types.md#三总表界面名--判定--转换策略)。

我们对 `doc2markdown` 的产物只做**两处**后处理：反转义（§六）与双链改写（§9.1）。两处都只作用于 `html2Doc → doc2markdown` 这条路，Lite Markdown 的正文是用户手写的原文，一律不动。

唯一的例外是**大纲笔记**：它的正文不是 doc，整条路都不同 —— 自己遍历 `div.node` 树生成嵌套列表（§9.2），既不过 `html2Doc` 也不做反转义。

### 9.1 协作笔记的双向链接（wiki-link）

doc 里它是**行内文本属性**（不是独立块）：

```json
{ "insert": " ", "attributes": { "type": "wiki-link", "name": "目标笔记标题",
  "linkId": "<目标笔记的 guid>", "id": "xxxxxxxx", "box": true, "created": 1770864306635 } }
```

`doc2markdown` 把它序列化成**应用自家方言** `[[<name> id=<linkId>]]`。那段 `id=<guid>` 让主流渲染器（Obsidian / 思源 / Logseq）**解析不出来，只当纯文本**，所以导出时去掉它：

```
[[名称 id=<guid>]]   →   [[名称]]
```

代价（刻意的取舍）：丢掉 `linkId` 这个**稳定锚点**，从此按标题匹配 —— 目标改名后就指不准了；`name` 本身还是**创建链接那一刻的快照**。

几条边界：

- **只作用在协作笔记上**（`noteType === 'Collaboration'`）。Lite Markdown 笔记的正文是用户手写的 markdown，里面的 `[[…]]` 是原文，绝不能动 —— 与 §六 的反转义是同一条约定。
- 只认“带 `id=<36 位 guid>`”的形态，普通 `[[名称]]` 原样不动。
- 名称里不允许有 `[` `]`（否则边界无法确定），所以**用户手打在双链外面**的那对方括号会被保留：`[` + `[[名称 id=guid]]` + `]` → `[[[名称]]]`。那不是我们多出来的括号，用户本来就打了 `[` `]`，`doc2markdown` 把它转义成 `\[` `\]`，我们的反转义又还原回来。

**实测（2026-10-04，xapp 0.1.107）**：

- 含双链的协作笔记样本确实存在（样本清单见 `docs/private.local/samples.md`）；行内属性类型只见到 `wiki-link` / `math` / `br` / 无。抽查普通笔记的 HTML，`wiki` / `linkId` 标记均未命中 —— 这个特性只在协作笔记里。
- 两种形态都实测过导出：只插一个双链 → `[[目标笔记标题]]`；双链外面用户自己打过 `[` `]` 的 → `[[[目标笔记标题]]]`（那对方括号是用户本来就打的，不是我们多出来的）。
- 回归：一篇带附件的普通笔记导出结果一字未变（`图片 1/1 · 附件 1/1`）；抽查 Lite 笔记的正文里 `[[` 均未命中（当前没有暴露面，但类型闸门照旧保留）。

> **没做的方案**（讨论过、按 B 结论搁置）：转成批次内的相对链接 `[名称](../目标/目标.md)`（需要把"批次路径表"从 `exportNotes` 传进 `renderNote`，并在多篇导出时预分配文件夹名），或补一节“双链”把 `linkId` 留在文末，以及**反链**。真要做得留 `linkId` 的话，现在这条改写是唯一要改的地方。

### 9.2 大纲笔记：`div.node` 树 → 嵌套列表

大纲笔记（`Outline`）**不走 `doc2markdown`**，它有一条自研转换（`src/export/outline.ts`），因为它的正文是一棵纯 `div.node` 树、而不是 doc：

```html
<body class="wiz-editor-body" data-wiz-document-type="outline">
  <div class="outline-container">
    <div class="node">
      <div class="row">
        <div class="operator-container">…折叠箭头 / 圆点…</div>   ← 纯装饰，丢掉
        <div class="content">节点文本</div>
      </div>
      <div class="child children">                               ← 子节点容器；叶子没有它
        <div class="node">…</div>
      </div>
    </div>
  </div>
</body>
```

**为什么不走通用路径**：那条路的 HTML→doc 是 Turndown + marked，实测会把整棵树**抹平**成一串平级 `* 文本`，还夹着 `\*` 转义垃圾。

**为什么自研转换这么小**：doc 层本身是好的（实测 `markdown2Doc → doc2markdown` 对嵌套列表**逐字节往返一致**），所以只要产出嵌套列表文本即可；而且大纲节点是**纯文本**（抽查的节点 `content` 里没有任何子元素）、没有图片 / 附件 / 批注，唯一的难点就是层级。

转换规则（与 `doc2markdown` 的无序列表**逐项对齐**）：

| 项 | 值 | 依据 |
| --- | --- | --- |
| 缩进 | 每层 3 空格 | `doc2markdown` 自己渲染无序列表就是这个缩进 |
| 项目符号 | `*` | 同上 |
| 文本转义 | 应用自己的 `escapeMarkdownText()` | 节点文本按字面渲染；实测它对 `A -> B`、`x < y` 这类无害文本不动手 |
| 空节点 | 写 `&nbsp;` 占位 | 只写 `*` 在 markdown 里是**分隔线**，语义会变（暂无样本，防御性处理） |
| 折叠状态 | 不参与判断，按 DOM 树全量导出 | 实测：编辑器里折叠节点后再导出，**内容完整**；导出读到的 HTML 里父节点全是 `switch.active`、子节点齐全 |
| 反转义 | **跳过** | 转义是我们故意加的（节点文本是纯文本），不能像富文本那条路一样还原 |

**验证**：拿真实大纲笔记与从 HTML 树独立推出来的期望值**逐行比对**，产出的 markdown **完全一致**（节点数、缩进、文本、转义全对）；勾“同时导出原始 HTML”时另存的 sidecar 仍保留完整 `outline-container` 结构、脚手架已剥、无 `opacity: 0`。

> **折叠状态（2026-10-04 补测）**：不用管它 —— 它是**纯编辑器的界面状态**，不持久化（关掉笔记再打开就恢复展开），也不改动笔记内容（`docParams` 与 localStorage / sessionStorage 里都没有折叠相关记录）。导出的还是全部节点，**笔记开着、节点已折叠时导出内容依然完整**。根因是导出**不读编辑器的实时 DOM**，读的是本地数据服务渲染的 `/ks/note/view/…/index.html` —— 那份 HTML 里父节点全是 `switch.active`、子节点齐全。

## 十、批量导出的服务端压力与对策

导出链路按环节分层，各自的请求量：

| 环节 | 服务端请求 |
| --- | --- |
| 读协作笔记的本地 doc JSON | 0 |
| 协作笔记联网同步 | ⚠️ 开一条 WebSocket 把整篇文档拉下来，每篇 1 次 |
| 读 `index.html` | ⚠️ SW 拦截器第一步会 `getDoc(kb, doc)`，本地没有就会触发一次服务端下载 |
| 下载图片 | 每张 1 次（量级最大） |

采取的措施：

- **请求节流：一个限速器管住所有后端请求**（`app-bridge.ts` 的 `requestPacer` / `pacedFetch()`）。规则是“**网络请求的起始时刻之间至少隔 60ms**”，而**不是**“每个请求结束再睡 60ms”：
  - 按**起始**计 ⇒ 一次本来就慢的请求（几百毫秒）已经把间隔吃掉了，后面不再白等。实测（合成响应）：300ms 的那次，两次请求起始间隔 **310ms**（没有额外 +60ms）；3ms 的那种才补到 **66ms**。
  - **本地命中不占名额**（`cameFromCache()` 读 Resource Timing 的 `deliveryType === 'cache'`）：本地数据服务应答一次只要 3~29ms，旧实现还要在后面白等 60ms。实测同一篇 5 张本地图：单次 3~16ms、**起始间隔只有 3~5ms**（旧实现是 5×60 = 300ms 的固定睡眠）。
    ⚠️ 两个坑都踩过：① 判定必须**推迟到下一次领号时**做 —— timing 条目要等响应体读完才出现（只拿到响应头就查，查不到）；② 请求地址可能是**协议相对**（`//wiznote-desktop/…`）而条目里存的是绝对地址，不归一化永远查不到。拿不到条目 / 字段不支持（`deliveryType` 不是 Baseline：Firefox 稳定版没有、Safari 26.4+、Chrome 117+）一律按“走了网络”处理 —— 判错方向只能是“多等一会儿”。
  - **覆盖面**：图片、附件、正文 `index.html`、评论、附件清单与详情**都走同一个节流器**（以前只有图片 / 附件那两个循环有延时，批量导出时正文请求是连着发的）。
- **网络失败重试一次**（`attemptCandidates()` / `pacedFetchWithRetry()`）：候选地址跑完**一个 HTTP 响应都没拿到**（每次都是 `fetch` 抛异常 ⇒ 更像本地服务 / 网络抽风，而不是“资源不存在”）时，隔 400ms 把整条序列重走一遍；正文 / 评论 / 清单这类单地址请求同理。**资源真的缺失时服务端会回 404 / 占位页（那是有响应的），所以正常路径一次都不重试** —— 实测：全抛异常那趟是 4 个候选各 1 次 → 等 409ms → 第二趟首发命中（拿到的是真图）；缺失资源那趟 3 个候选各只请求 1 次、零重试。
- `允许联网补全` **默认开启**（笔记量大且多数没在本机打开过时，只有开启才能导全）。关闭它会先查本地 IndexedDB（主库的 `docs` / `data` 表），查不到就跳过并在结果里说明原因，完全不碰服务端。预检面板会实时显示“关掉会跳过几篇”，方便按需切换。
- 导出前的预检不产生任何请求，**先看清范围再决定要不要开始**。
- **任务之间也串行**：导出期间再提交的导出会排队（§1.5），不会两个任务同时打服务端。
- 导出后把“跳过 / 失败 / 图片失败”逐条列出，不静默略过。
